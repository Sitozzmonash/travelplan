# 入库这一步应该由 LLM 用 tool call 决定，而不是代码全收

> 记录时间：2026-09-21
> 来源：用户在看「探索确认」页发现同义子 POI 扎堆后，指出的**架构层面**的问题（不只是去重问题）
> 本文件只记录诉求与现状差距，不含实现。

## 一、用户要的形态（agentic plan）

```
小红书搜攻略
  → LLM 提取出：地点 / 景点 / 饭店（光名字）
  → 高德验证（拿回真实 POI：坐标、类型、地址、营业时间、商圈…）
  → 把高德这批结果交给 LLM
  → LLM 通过 function call 调用「入库工具」，决定入什么、怎么归类
      高德返回的有用信息不能遗漏，一并交给 LLM 去 call tool 入库
```

一句话：**"哪些该入库、归到哪个池、同一景点的子设施怎么合并"是 LLM 的判断，不是代码的 `for` 循环。**

## 二、现状：代码全收，LLM 只在最前面出个名字

`app/discovery.py::extract_place_candidates`（约 611-663 行）实际做的是：

1. 攻略 → 模型抽地名 → `raw_names`（模型只给**名字**，例如"杜甫草堂"）；
2. 对每个名字调高德 `search_poi(term, destination, page_size=10, type_hint="attraction")`
   —— `poi_page_size` 默认 **10**（`app/config.py:89`）;
3. **把高德返回的这一页全部收下**，只按 `place_id` 去重：

```python
for place in poi.items:
    if place.place_id in seen_ids: continue
    seen_ids.add(place.place_id)
    places.append(place)          # ← 全收，没有任何判断
```

4. `planner.dedupe_places()` → 按 `user_visible_poi_limit`（默认 20）**按攻略提及顺序截断**。

归类也不在入库时发生，而是事后由关键词表猜：`app/selection.py::place_category()` 用 `name + type` 做子串匹配，**兜底 `return "attraction"`**。

### 关键事实：这个仓库里没有 function calling

`app/` 下没有任何 `bind_tools` / `tools=` / `tool_calls` / `tool_choice`（`tool_calls` 那些命中是 `run_metrics` 里的**调用计数器**，与 LLM 工具调用无关）。所有 LLM 交互都是"prompt → 返回 JSON"这一种形态：`parse_intent`、`query_expansion`、`extract_places`、`preference_profile`、`critic`、`final_answer`、`llm_rank_candidates`。

也就是说：**"让 LLM 调工具入库"这件事，当前连基础设施都没有。**

## 三、差距带来的可观测后果

代码替 LLM 做了"要不要入库 / 归哪类 / 留几条"三个判断，每一个都在线上出了错（同一天的另一个问题记录见
[`2026-09-21-探索确认-候选地点重复与误分类.md`](2026-09-21-探索确认-候选地点重复与误分类.md)）：

| 代码替 LLM 做的判断 | 实际结果 |
| --- | --- |
| 高德返回的都入库 | 成都 20 条候选里，杜甫草堂 5 条、宽窄巷子 7 条、熊猫基地 6 条 —— 只对应 **4 个真实景点** |
| 事后用关键词猜分类、兜底"景点" | 杜甫草堂(地铁站)、熊猫基地迎迎停车场、桔子水晶酒店 全被当成景点 |
| 按攻略提及顺序截断 20 | 前 3~4 个地名各自返回 10 条，就把 20 个名额吃光，**后面的地名一个都进不来** |

这些都不是"去重没写好"，而是**入库决策权放错了地方**：高德是检索工具（会返回一堆近似结果），它不该被当成"候选集合的最终裁决者"；裁决者应该是 LLM。

## 四、期望的形态（供以后实现时对齐）

1. **保持现状不变的部分**：攻略检索、模型抽名、高德搜索与详情；**事实仍以高德为准**（坐标、地址、营业时间、类型、价格一律由高德给，LLM 不得改写 —— 这条红线与现有 `docs/14` §3 一致）。
2. **新增**：把高德这一批结果（含 `place_id / name / type / address / location / business_area / district / opening_hours / rating`）作为**工具结果**交给 LLM。
3. **LLM 通过 function call 调用入库工具**，由它决定：
   - 这条高德 POI 是不是用户要的「景点 / 饭店」（地铁站、停车场、售票处、酒店直接不入）；
   - 归到哪个池（景点 / 美食 / 体验）；
   - 同属一个景点的多个子设施怎么表达（留一个母体 + 其余作为附属信息，而不是并列候选）；
   - 高德字段里哪些对该地点有意义（不遗漏有用信息，也不塞无用字段）。
4. **代码只做两件事**：执行 tool call、校验参数（例如 `place_id` 必须真实存在于刚才那批高德结果里 —— 防止模型编造）。
5. **必须保留确定性兜底**：LLM 不可用 / 超预算时退回现状行为（宁可给一份粗糙候选，也不能空榜）—— 这与仓库既有的"真实优先、降级披露"一致。

## 五、规模上的提醒

这是**架构级改动**，不是一处去重补丁，至少涉及：

- LLM 客户端要有工具调用能力（现在只有 `invoke_json`）；
- 要定义入库工具的 schema 与执行器（写 `city_pois` / `places`）；
- `extract_place_candidates` 的"全收 + 截断"要改成"组装工具结果 → 收 tool call → 落库"；
- 会新增一类审计需求：**每一次 tool call 都要留痕**（谁被入、为什么被丢），否则"LLM 判错了"无法复盘 —— 这正好接上仓库现有的 Trace / Bad Case 机制。

## 六、实现方式：用 SuperHarness 的 function call

> 用户 2026-09-21 追加要求：**"这些要用 superharness 框架，function call"**

### 6.1 能力已经在了，travelplan 没用

SuperHarness 本身就是**带工具调用的 LangChain agent 框架**：

| 已有能力 | 位置 |
| --- | --- |
| agent 装配（可传 `tools=` / `mcp_servers=` / `middleware=` / `subagents=`） | `superharness/agent.py::create_harness_agent` |
| 本地工具装载 + 名称冲突检查 | `superharness/agent.py::_build_local_tools` |
| 工具动态注入与路由（BM25 / LLM / Hybrid，`tool_top_k` / `mcp_tool_top_k`） | `superharness/capabilities/middleware.py::CapabilityMiddleware` |
| MCP 工具加载 | `CapabilityMiddleware` 内的 `mcp_loader.load_tools()` |
| 模型/工具重试中间件 | `langchain.agents.middleware`（`ModelRetryMiddleware`、`ToolRetryMiddleware`） |
| 两条路由 | `Route.WORKFLOW`（固定流程）/ `Route.AGENT`（Agent Loop），见 `app/agent.py::run_travel` |

**现状**：travelplan 的 quick 与 guided **都走 `Route.WORKFLOW`**，也就是自己那套固定节点；节点里的 LLM 交互被收窄成 `app/llm.py` 的 `invoke` / `invoke_json`（**没有 tools 参数、没有工具循环**）。`Route.AGENT` 那条路存在但不用。

所以要做 function call，正路是**把需要 LLM 决策的那几步改走 harness 的 agent + tools**，而不是在 `discovery.py` 里手搓一个"调模型 → 解析 tool_calls → 执行 → 回灌结果"的循环 —— 那等于把 harness 已经做好的东西（工具路由、重试、留痕）再写一遍。

### 6.2 全仓需要 LLM 参与的地方（就这 9 处 + Jev）

| 现状 tag | 位置 | 干什么 | 性质 | 该走工具决策吗 |
| --- | --- | --- | :---: | :---: |
| `parse_intent` | `workflow.py:1602` | 一句话 → 结构化意图 | 判断 | 待定 |
| `query_expansion` | `discovery.py:295`、`workflow.py:2209` | 生成攻略检索词 | 生成 | 否 |
| `extract_places` | `discovery.py:494` | 攻略正文 → 地点名 | 抽取 | **是（抽完即入库）** |
| `extract_places_retry` | `discovery.py:520` | 批失败后单篇重试 | 抽取 | 同上 |
| `preference_profile` | `decision/profile.py:79` | 生成动态偏好画像 | 生成 | 待定 |
| `llm_ranking` | `decision/planner_decision.py:201` | 在候选方案里选一个 | **决策** | **是** |
| `critic` | `workflow.py:4084` | 审查行程、提质疑 | **决策** | **是** |
| `final_answer` | `workflow.py:5110` | 行程 → 中文说明 | 生成 | 否 |
| Jev（外部决策服务） | `decision/jev.py` | `plan_choice` / `tradeoff` / `quality_gate` | **决策** | **是（或继续用 Jev）** |

注意：**"入库"本身不在这个表里** —— 它现在完全没有 LLM 参与，是 `discovery.py` 里一段纯 `for` 循环。要给这一格补上，补的形态就是"走 harness 的 tool call"。

### 6.3 一个必须先解的冲突

仓库里有一条测试**专门断言"模型只在 6 个调用点被问"**：

`tests/test_workflow.py::test_the_model_is_only_consulted_at_the_documented_sites`

它把 prompt 集合钉成 6 个常量。一旦引入工具调用（哪怕只是给入库加一个 tool），这条断言必然失败。所以改之前要先决定：

- 是把这条断言**改成"调用点白名单 + 工具白名单"**（承认 agent 化是既定方向），
- 还是限定"只有入库这一步走 agent，其余仍走固定流程"（把 agent 化的范围框住）。

这个决定影响 `docs/14` §3「Python 只负责硬规则、LLM 只负责软决策」那条红线怎么表述 —— 现在它默认"决策都由 Python 显式编排"，而 tool call 意味着**编排权部分交给模型**。
