# 探索确认页候选地点：同一景点拆成一堆子项

> 记录时间：2026-09-21
> 来源：用户在看 `/guided` 的「探索确认」页时发现（重庆 → 成都，3 天）
> 现象：成都杜甫草堂写了六个、宽窄巷子五六个、成都大熊猫五六个；而且「杜甫草堂(地铁站)」被当成景点。
> 本文件只记录问题与根因，不含修复。

## 一、先回答"怎么重复的"：**一次里就重复，不是多次堆叠**

直接查预热写进 Neon 的 `city_pois`（去重键是 `(city, place_id)`），成都一共 **20 行**，就是一次抽出来的结果，没有跨次累积。20 行按"母体"归并后是这样：

| 母体 | 条数 | 具体行 |
| --- | ---: | --- |
| 杜甫草堂 | 5 | 成都杜甫草堂博物馆 / 成都杜甫草堂博物馆正门售票处 / 杜甫草堂(地铁站) / 杜甫草堂-大雅堂 / 杜甫草堂-草堂南邻 |
| 宽窄巷子 | 7 | 宽窄巷子(B口) / 宽窄巷子(地铁站) / 宽窄巷子·宽厂 / 宽窄巷子景区-窄径 / 宽窄巷子步行街 / 成都宽窄巷子城际酒店(旗舰店) / 成都宽窄巷子桔子水晶酒店 |
| 成都大熊猫繁育研究基地 | 6 | 基地本体 / -熊猫塔 / 扩建区 / 游客中心B区 / 西门游客中心 / 迎迎停车场 |
| 乐山大佛 | 2 | 乐山大佛 / 乐山大佛文化广场游客中心 |

**20 个候选只对应 4 个真实景点**，其余是同义词子项。行数没有膨胀（不会越用越多），是**这 20 个位置本身没被当成"4 个景点"来收敛**。

## 二、三条独立机制，缺一条都不会这么难看

### 1. 去重键是 `place_id`，而子设施的 `place_id` 天生不同

`city_pois` 的主键、`split_poi_pools()` 里的 `place_id not in pools[pool]`（`app/discovery.py:784`）都以 `place_id` 为唯一性判据。而"杜甫草堂博物馆"和"杜甫草堂(地铁站)"在高德是两个真实且不同的 POI，各有各的 id —— 所以这类重复**永远不会被去重掉**，去重逻辑本身没有错，是它管不到这一层。

### 2. `place_category()` 的兜底是"景点"

`app/selection.py:487`：

```python
def place_category(place: Place) -> str:
    haystack = " ".join([place.name, place.type or "", place.business_area or "", place.district or ""])
    for category, keywords in _CATEGORY_KEYWORDS:
        if any(keyword in haystack for keyword in keywords):
            return category
    if place.type and any(term in place.type for term in ("餐饮", "美食", "restaurant")):
        return "food"
    return "attraction"        # ← 兜底
```

**不命中任何关键词 → 一律 `attraction`**。于是地铁站、停车场、售票处、游客中心、服务中心全被归进景点池：

- `杜甫草堂(地铁站)` type = `交通设施服务;地铁站;地铁站`
- `成都大熊猫繁育研究基地迎迎停车场` type = `交通设施服务;停车场;公共停车场`
- `成都大熊猫繁育研究基地游客中心B区` type = `生活服务;信息咨询中心;服务中心`
- `成都宽窄巷子桔子水晶酒店` type = `住宿服务;宾馆酒店`

—— 这些高德**明确给了类型**，代码却没按类型拦，直接吃了兜底。

### 3. 关键词表会误伤，把子设施"救"进景点池

`_CATEGORY_KEYWORDS`（`app/selection.py:475`）按子串匹配，而 haystack 里含 `name`：

| 关键词（所属类别） | 命中了谁 | 后果 |
| --- | --- | --- |
| `草`（`nature`） | **杜甫草堂** | 含"草"→ nature → 景点池。所以连"杜甫草堂(地铁站)"都跟着变成景点 |
| `熊猫`（`family`） | 熊猫基地**迎迎停车场** | 停车场也进景点池 |
| `塔`（`nightview` / `history`） | 熊猫塔、大雁塔类 | 子景点被单独归一类 |
| `餐`（`food`） | `宽窄巷子(B口)`（高德类型是餐饮相关场所） | 一个地铁出口进美食池 |

"草"是为草原/草地准备的，"塔""江"这类单字词在中文地名里歧义很大。

## 三、附带发现：跨市越界

成都的缓存里混进了 **乐山大佛**（乐山，不是成都）。说明按关键词向高德检索时**没有按目的地做地理围栏**，邻市的热门景点会被带进候选。

## 四、影响

1. 用户在「探索确认」页做勾选时，**同一景点要判断五六次**，还得自己分辨哪个是"本体"——这正是"想少填信息"的反面。
2. 把停车场/地铁站/酒店当景点列出来，是**事实性错误**（用户会直接怀疑数据质量）。
3. 候选池被同义子项挤占：真正的独立景点只剩 4 个，`MAX_PLAN_CANDIDATES`、每日 POI 数量、Top-K 比选全都建立在"这 20 个是不同的景点"这个错误前提上。
4. 这个问题**与预热无关**，预热只是把一份本来就这样的候选原样搬进了共享库，于是所有会话都会看到同一份。

## 五、可能的方向（未实施，供讨论）

- **抽数时就收敛母体**：高德返回后按"归一化主名"聚簇（去掉括号后缀、去掉"游客中心/停车场/售票处/地铁站"等设施词），每个母体只留一个代表 + 保留其余作为"同景点的入口/设施"备注，而不是当成并列候选。
- **按高德类型硬拦**：`type` 里是地铁站/停车场/售票处/咨询中心/酒店的直接不进景点池（高德的类型已经是结构化的，比关键词可靠得多）。
- **兜底改成"不分类"而不是"景点"**：现在 `return "attraction"` 让"分类失败"静默伪装成"这是个景点"。改成 `experience` 或直接不进池，失败就会显式暴露。
- **关键词表加边界**：单字词（草、塔、江、面、餐）改成词或与 `type` 联合判断，避免"杜甫草堂 → 草原"这类误伤。
- **检索加地理围栏**：按高德的城市/区县限定，避免邻市串味。

## 六、已有数据怎么办（补记）

### 6.1 现存体量

| 表 | 行数 | 说明 |
| --- | ---: | --- |
| `city_pois` | 400 | 20 城 × 20 条，**全部带同类问题**（子设施扎堆 + 误分类） |
| `city_evidences` | 213 | 全为网页来源（`source_type='web'`），本身没坏 |
| `city_cache_meta` | 20 | 检索词，本身没坏 |
| `city_poi_mentions` | 0 | 本来就是空的（见另一个问题记录） |

另外 run 级的 `places` 表里也有这些子设施，但它们绑在历史 run 上、是历史记录，**不该动**（改了会断掉那次 run 的证据链）。

### 6.2 关键：**放着不管不会自愈**

四条机制叠起来，脏数据会被一直用下去：

1. **过期不等于读不到**：会话走的是 `read_candidates(..., allow_stale=True)`，过期数据照样回吐兜底；
2. **清理只在写入时发生**：`prune_city_cache()` 是 `write_candidates()` 末尾才调的 —— 没人写，超期行就一直躺着；
3. **写新数据覆盖不掉子设施**：upsert 键是 `(city, place_id)`，而"杜甫草堂(地铁站)"和"杜甫草堂博物馆"是**不同 place_id** —— 新的一次预热只会再加一批，不会顶掉旧的；
4. 于是**用得越久，堆得越多**。

结论：**必须显式处理，不能靠时间。**

### 6.3 三个可选做法

| 做法 | 操作 | 代价 / 风险 |
| --- | --- | --- |
| **A. 清库重建（推荐）** | 删掉这 20 城在 `city_pois` / `city_poi_mentions` / `city_evidences` / `city_cache_meta` 的行 → 代码修好后跑 `scripts/preheat_cities.py` | 约 2.5 分钟/城 × 20 ≈ 45 分钟。**不依赖 TikHub**（现在的缓存本来就是网页来源，Tavily + 高德都正常） |
| **B. 就地清洗** | 写一次性脚本：按类型筛掉地铁站/停车场/售票处/酒店，再把同义子项按主名合并 | 清洗规则**就是待改的那套规则本身**；用旧规则洗一遍意义有限，且容易洗出新的错 |
| **C. 只删不重建** | 直接删掉这 20 城的行，让用户访问时走实时 Discovery | 立刻止血（不再看到脏候选），但用户要等 3~5 分钟实时跑，且实时跑出来的候选**同样会重复** —— 因为问题在代码里，没修之前重建也是脏的 |

### 6.4 顺序上的一句话

**先修代码，再清库重建。** 顺序反了（先重建后修）等于白跑一遍 45 分钟，拿到的还是同样的 20 条。

清库时可以只删要重建的城市、不必整库清 —— `preheat_cities.py` 支持 `--cities` 指定城市，逐城替换更可控。
