# 引导页攻略推荐、实体去重与规划交接

日期：2026-09-22
状态：已核实线上数据；四条链路的代码修复与离线回归已完成，未提交、未部署。

## 范围与目标

用户所称“第一页”是基础出行信息，“第二页”是 `/guided` 的探索确认页，下一页是交通、酒店、节奏偏好，之后进入正式规划。

第二页应只做攻略发现与推荐：LLM 调用数据库攻略/地点召回工具和 Web 搜索工具，综合两路证据后调用结构化推荐输出工具，展示住宿区域、美食、景点、特色体验与商圈。机票、酒店产品查询留给正式规划。

用户有明确正向选择时以选择为规划输入；没有正向选择时用本次 LLM 推荐清单，不用未筛选的整个城市缓存。负向选择始终排除。

本轮仅修改本地代码、测试及本反馈。不提交、不推送、不部署、不清理生产数据库；历史数据清理须另行审阅影响范围。

## 线上核实证据

核实入口：[北京到成都，5 天，2 人](https://travelplan-web.vercel.app/guided?origin=%E5%8C%97%E4%BA%AC&destination=%E6%88%90%E9%83%BD&start_date=2026-09-22&duration_mode=days&travelers=2&budget_mode=amount&days=5)。

浏览器真实页面加载创建会话 `ps-20260922-055708-37f817`，随后通过只读 GET 查看会话、成都城市缓存及健康状态，未点击正式规划。生产健康接口返回 PostgreSQL 已连接。

1. 页面同时显示“正在查询交通”“正在比较酒店”“正在阅读旅行攻略”，以及“正在整理攻略，已找到 20 个地点”。会话状态为 `DISCOVERING` / `RUNNING`，已展示数据来自 `city_cache`，交通和酒店产品候选均为空。仅凭这些文案不能证明供应商请求已经发出，需结合后端调用链核实。
2. 成都缓存共 20 个地点，10 个在大邑县。住宿区域首推“大邑县”，分数 0.5329，理由是“10 个候选地点，50% 的攻略在此区域有提及”。对没有要求大邑度假的成都城市游，这不是合理的默认推荐依据。
3. 8 个美食候选均为大邑县茶馆；“茗香茶坊(迎宾大道店)”和“鹤鸣道茶”被归为商圈；“成都欢乐谷水世界(暂停营业)”进入特色体验。说明还存在召回偏差、分类与营业状态问题。
4. 两个“人民公园”分别为青羊区 `B001C7X8QA` 和简阳市 `B0340005AB`，坐标距离约 55.0 km。它们不是应按名称合并的同一实体。需要目的地范围筛选与同名消歧，而非全库同名删除。另有“文殊院/文殊坊文殊院历史文化保护区”等主景区和范围实体，需区分实体关系与推荐卡片层的重复体验。
5. 缓存有 8 条攻略证据、2 条已关联地点的 mention，但界面全部 20 个候选显示 `evidence_count=0`。住宿理由里的“50%”也不能直接当作全城攻略覆盖率。
6. 稍后只读 GET 同一会话，酒店产品候选从 0 增加到 8，而会话仍为 `DISCOVERING` / `RUNNING`，地点保持 20 个。进一步证明第二页确实加载了酒店产品，不只是进度文案写错。

## 问题一：探索确认阶段混入交通、酒店查询

问题：用户只是选兴趣点，却进入整趟旅行的供应商发现阶段；候选已经显示后仍长期等待，文案也混淆“候选发现”和“推荐完成”。

优化方向：将攻略推荐阶段和正式规划的交通/酒店发现解耦。推荐阶段只能开放攻略数据库召回、Web 搜索、地点核验与推荐提交工具；状态文案必须对应实际阶段。已有缓存只能标记为候选或降级结果，不能冒充已完成的 LLM 推荐。

验收：创建推荐会话不调用航班/列车/酒店产品供应商；成功、降级和失败都能结束忙碌状态；正式规划仍可以查询实时交通与酒店。

## 问题二：数据库原始候选被当作推荐，住宿偏离主目的地

问题：城市行政范围大，缓存分布不代表适宜住宿分布；按 POI 数量占比推荐会把被错误召回的一批远郊茶馆放大为“大邑住宿优势”。

优化方向：采用两路工具召回（数据库攻略与地点、Web 攻略），将来源、地理范围、地点证据、营业状态一起给 LLM；由 LLM 输出类别与适配理由，再通过结构化提交工具校验 ID、来源及范围。住宿区域应根据主要活动范围、交通便利与行程适配推荐；远郊可保留为有说明的一日游/度假选择，但不默认压过市中心。不得硬编码一份成都景点表替代通用流程。

验收：推荐接口有可追溯双路证据和明确推荐清单；住宿原因不是简单候选计数；不将茶馆当商圈；不默认推荐已暂停营业项目；关联攻略的候选显示正确证据数量。

## 问题三：入库、查询、呈现的实体去重必须一致

问题：同一地点可有不同来源 ID、别名、主景区/子设施；不同地点也可能同名。只在前端按名字去重会掩盖脏数据并误伤异地同名实体。

优化方向：建立统一身份规则与 canonical ID，优先可信供应商 ID，其次归一化名称/别名加城市、行政区、地址和坐标邻近匹配。入库时合并同一实体并保留来源与别名，读取历史缓存时再次收敛并重映射 mention/选择；推荐输出与前端做幂等兜底。主景区/子设施只有关系充分时才折叠，不能单凭名字包含关系误合并。跨区同名保留实体并带地区显示。

验收：同 ID、多源别名、旧缓存重复、跨区同名、远距离同名、商户不同分店、主子景区均有回归用例；合并后证据与选择不丢；不直接删除生产历史记录。

## 问题四：选中清单与默认推荐应贯穿正式规划

问题：用户需要“有正选就按所选，没有正选就按 LLM 推荐”，而不是 UI 勾选仅影响展示，或未选时重新从未筛选城市池任意规划。

优化方向：明确保存推荐候选 ID、推荐版本/状态和用户选择；正式规划依据正选优先、推荐兜底、负选永远排除的契约生成输入。返回修改、异步推荐完成和继续下一页之间不能覆盖用户已作出的选择。推荐尚未可用时应明确提示，不静默放大到整个原始缓存。

验收：必去、想去、未选、只做负选、全不感兴趣、推荐未完成、往返页面及失效 ID 都有测试；缺少餐饮等类别可以合理补足，但不能加入被排除地点或替换用户正选。

## 修复落地

四条链路各自的实现：

1. 第二页只做攻略推荐。`sessions.run_discovery` 不再调用 `discovery.prefetch`，也不查交通/酒店产品；新增 `app/recommendations.py`，用原生 function calling 依次调用 `recall_city_guides`（数据库攻略+POI+真实 mentions）、`search_web_guides`（Web 攻略，只从正文抽取具体名称再核验）与 `submit_recommendations`（结构化提交）。提交受校验：ID 必须来自本次召回、引用必须属于该地点的本次证据、闭业/暂停营业与附属设施不可推荐、专卖茶店的购物服务不能升格为商圈、同名跨区不合并。模型只回自然语言或 JSON 文本时按失败处理，降到 `evidence_fallback` 且标 PARTIAL，绝不冒充 LLM 推荐。
2. 住宿不再按 POI 数量推荐。住宿区域必须有明确推荐该区域住宿的攻略句子 + 关联活动点 + 地理校验（市中心距离、远郊需用户明确要求），缺依据宁可留空；`node_search_hotels` 不再用原始 POI 密度覆盖已确认的推荐区域。
3. 存取展示统一去重。`places.PlaceResolver` 与 `planner.dedupe_places` 共用同一套硬冲突（城市、分店、距离、区县），union-find 做簇级冲突保护；`city_cache` 读写都走共享去重并往返保留 aliases/merged_from/source_id，mention 按证据正文消歧而不是按裸名任取；`discovery.resolve_pois` 改为先 ingest 再登记每个检索词的完整命中。
4. 规划交接按“正选优先、推荐兜底、负选排除”。`start_run` 只把所选子集交给正式 run，并同步收窄住宿区域；推荐未就绪/不可用/选择非法/全被排除都返回明确的 409 而不是静默放大到整个城市缓存。
