## 1. A15：Dashboard 冷加载仍要解析 plan_json（「Run 完成即存质量摘要」未做）

- 现状：`app/admin_analytics.py::dashboard()` 对最近 `quality_sample`（默认 10）个 run 逐个
  `plan_snapshot` 解 plan_json 算质量分。45s 的整页缓存解决的是"重复打开"，**第一次冷加载
  仍然慢**（Neon 上单次 plan 读取约 1~2s）。
- 已做的一半：`_DASHBOARD_TTL_SECONDS=45` 整页缓存 + `run_contexts` 按 `session_id` 去重。
- 没做的一半：**Run 完成时把质量摘要写进 run_metrics**，dashboard 有快照就直接读、不再解析 plan。
- 为什么没做：牵动质量分"抽样 N 个 run"的口径 —— 有快照就能算窗口内全部 run，口径一变，
  前后端 hint（"抽样 N 个运行"）与历史数字就对不上。怕引入两处口径打架，所以只做了缓存那一半。
- 怎么补：
  1. `run_metrics` 加一列 `quality_score`（走 `_migrate_*` 模式，老库 ALTER）；
  2. `workflow.persist_metrics` 里算 `_quality_score(planner.plan_quality(...))` 写入；
  3. `dashboard()` 优先用列值，缺列值的旧 run 才退回解 plan_json；
  4. 前端 hint 同步改成"窗口内全部 N 个运行"（如果决定用全量口径）。

## 2. Trace 的 `context_preview` 恒为 null（无调用点传 context）

- 现状：`LLM.invoke(system, user, *, tag, context=None)` / `invoke_json` 参数已就绪，
  传入时真正发出去的消息是 `[System, Human(user + "\n\n" + context)]`，`to_audit()` 也会拆出
  `context_preview`。但**没有任何调用点传 `context`**，所以管理端 Trace 的 Context 行永远是空。
- 为什么不补：system / user / assistant 预览已经能回答"模型实际收到了什么、回了什么"；
  把注入的正文/计划从 user 里拆出来传 `context=` 是纯展示层收益，且涉及 `extract_places` /
  `critic` / `final_answer` / `llm_rank_candidates` 等多处调用点的文案分工判断，留到有明确
  需求再做。
- 怎么补：挑语义最清晰的一处（例如 `final_answer`：system=成文指令、user=行程摘要、context=plan 的
  `_digest_json`），其余照抄。

## 3. A17 后半没做：自动学习 Alias / Resolver Benchmark / 错并漏并 Bad Case

- 现状：只做了"低置信度不合并"的保守保护（漏并比错并安全）和 §22 六条验收单测。
- 没做：
  - **自动学习 Alias**：低置信度 match 的人工审计 → 确认后自动写进 `place_aliases`；
  - **Resolver Benchmark**：对一批已知 (地名 → 实体) 用例回归 Resolver 的并/漏并率；
  - **错并 / 漏并 Bad Case 收集**：接入 `badcases` 机制，人工审计入口。
- 前置：需要先有一套"已知正确答案"的评测集（现在连收集入口都没有）。

## 4. 社媒证据仍为 0（TikHub 额度耗尽，非本轮回归）

## 5. 婺源 / 大理一度写入未过滤原始候选（已修 + 已重建）

- 现象：地理围栏把整城候选清空（高德 `cityname` 是地级市：`上饶市` / `大理白族自治州`，
  与目的地"婺源"/"大理"都不相等），兜底又把**未过滤**的原始候选（含酒店/收费站）写进缓存。
- 修复：`places.place_in_city` 判定放宽到"城市相关 ∪ 行政区相关 ∪ 两者都缺才放行 ∪ 都有值
  却不相关才拒收"，`city_related` 容许 `大理` ⊂ `大理白族` 前缀；`resolve_pois` 兜底分两级
  （先退回"已剔设施/地址桩"的候选，再退真正未过滤的）。两城已重建并自检通过。
- 注意：如果在 00:16–00:20 之间访问过这两座城市，看到的是修复前的脏数据；现在已是干净的。

## 6. 其它没做的小项

- **Resolver 留痕上限**：单次 ingest 只保留前 60 条（`MAX_TRACES_PER_INGEST`），高频的
  "Provider 引用复用"不逐条留痕（按词聚合）—— 够复盘，但不是逐 POI 全量。
- **`canonical_places.category`** 是冗余展示字段，重建时按当时的 type 分类写入；分类规则
  后来改过（购物/风景名胜优先级），老实体行的 category 不回填 —— 展示层用的是
  `place_category(place)` 实时算的，不受影响。
- **低置信度人工审计入口**（方案 §20 P2）：管理端还没有"实体层待确认合并"的列表接口。
