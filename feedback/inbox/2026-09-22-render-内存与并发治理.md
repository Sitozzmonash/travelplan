# Render 内存与并发治理（2026-09-22 诊断）

> 状态：**1~3 已实施（2026-09-22），4~6 保留 / 未实施**。用户拍板「可以按你说的办」。

## 1. 现象

Render 后端 `travelplan-api`（free / ohio / **512MiB**）被 OOM 杀过至少两次：
- `2026-09-22T06:13:04Z` —— `oomKilled memoryLimit 512Mi`（**改造前就有**）
- `2026-09-22T14:28:43Z` —— `oomKilled memoryLimit 512Mi`；当时 `tp-20260922-142521-968747`
  这个 run 从 `14:25:21` 一直跑到被杀，**单个真实 run 就能把免费档撑爆**。

查日志命令：`render logs -r srv-danu823m8hqs73cj67ng --start <ISO> --end <ISO> -o text --confirm`
查事件命令：`GET /v1/services/<id>/events?limit=N`（能直接看到 `oomKilled.memoryLimit`）。

## 2. 根因（本地实测数据）

1. **Python 进程基线 ~187MB**（`import app.api` 后），跑起来到 **~214MB**：
   FastAPI + LangChain/LangGraph + numpy（rank-bm25 带进来的）。**占 512MiB 的 ~40% 起步。**
2. **12306 MCP 用 npx 拉 node 子进程**：实测同时出现 `node.exe` 50MB + 65MB ≈ **+115MB**，
   和 Python 进程一起算进容器限额。且实测 `search_trains` 走 MCP 时 `UNAVAILABLE`、
   单次耗时 **107.6s**（最后靠途牛兜底且 0 条）。
3. **单进程 4 并发**：`app/api.py:185` `_RUN_EXECUTOR = ThreadPoolExecutor(max_workers=4)`，
   一个池子同时承载 5 类活：
   - `:311` 用户正式规划 run（`POST /api/v1/plans {background:true}`，最长几分钟）
   - `:568` 会话 Discovery（`POST /api/v1/planning-sessions`，`recommend_guided` 约 26s）
   - `:625` 会话启动正式 run（`/planning-sessions/{id}/start`）
   - `:1188` 管理端触发的 **benchmark 作业**（真跑 12 个 case 的 agent loop）
   - `:1518` 管理端触发的 **evolution 作业**
   → admin 点一次评测就能占满线程 + 抬内存，还可能把用户规划挤到排队。
4. **本次改造加重**：`execute_agent_run` **每次 run 全部重建** super_harness 装配
   （CapabilityRouter/BM25、MemoryManager→SQLite、RetrievalManager、中间件链、agent 图），
   而旧路径是「装配一次、全局复用」（`app/agent.py::_shared_app`）。
5. 基线之上还开着默认 `memory_enabled=True` / `retrieval_enabled=True`（`super_harness/config.py:48/73`，
   **是字面量、不能靠 env 关**），`**MemoryMiddleware` 会把每次 run 的 rollout 写进
   `data/memory.db`，攒够条数还会**再调一次模型**做 consolidation。

**合起来**：基线 ~190MB + 单 run 增量 + MCP node 进程 ~115MB ≈ **330MB**，
两个并发 run（或一个长 run 叠加轮询/会话）就跨过 512MiB。

## 4. Render 服务怎么分配（结论）

**不建议靠"再加一个/两个实例"横向扩**：
- Render 免费档没有自动扩缩，每个 web service 是独立 URL、各自会休眠（多一个 = 多一份冷启动）；
- 规划任务跑在**接了这次 POST 的那个进程**的后台线程里，加实例只是多开几个独立入口，
  不会分担同一个 run；真要分工得引入「队列 + 固定 worker」。
- 若将来真要横向扩：进度已经落库（`run_progress`/`run_stages`），轮询跨实例没问题，
  但任务本身不会迁移，必须做成队列消费。

**建议的分配（二选一）**：
- **省事版（推荐）**：**单服务 + 升档到 2GB**，同时做第 1~3 条瘦身。
- **隔离版**：拆两个服务 ——
  - A：生产 API（用户规划 + 会话 Discovery），关 MCP、并发 1~2、关 memory/retrieval；
  - B：重任务（admin 的 benchmark / evolution，以及将来的批处理），它崩了不影响用户。
    把 `:1188` / `:1518` 那两类任务从 A 挪到 B（或干脆只在本地/GitHub Actions 跑）。
  - 预热已经在 GitHub Actions 定时跑，不用管。
