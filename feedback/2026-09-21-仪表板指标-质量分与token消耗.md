# 仪表板指标：行程质量分 / 平均每个规划的 token / 总 token

> 记录时间：2026-09-21
> 来源：用户要求「仪表板把行程质量分、缓存平均 token 消耗 + 总 token 消耗 记上」，
> 随后明确：「**总 token = 历史累计**」+「**平均每个规划的 token 要加**」。
> 本文件只记录现状与缺口，不含实现。

## 一、要放的三项

| 指标 | 口径 | 现状 |
| --- | --- | :---: |
| 行程质量分 | 窗口内加权合成 | ✅ 已有 |
| **平均每个规划的 token** | 窗口内平均 | ❌ 缺 |
| **总 token** | **历史累计**（不分时间窗） | 🟡 有数，在折叠卡里 |

## 二、逐项对现状

| 指标 | 位置 / 缺什么 |
| --- | --- |
| **行程质量分** ✅ | 仪表板 KPI `quality_score`（`app/admin_analytics.py:901`，label「行程质量分」，`unit=ratio`，hint 带抽样运行数）；分数由 `_quality_score()`（`:439`）按权重合成。**什么都不用做** |
| **平均每个规划的 token** ❌ | `app/admin_analytics.py` 里**连 `total_tokens` 这个词都没有** —— token 完全没进仪表盘的时间窗统计。需要新增一个 KPI |
| **总 token** 🟡 | 口径要的就是现在这个：`app/api.py:487` 的 `/admin/overview` 对全部 run 求和 → 前端「累计用量（历史总量）」卡片（`dashboard-view.tsx:~458`）。**数已经有了**，只需确认展示位置 |

数据底座是齐的：`run_metrics` 同表就有 `input_tokens / output_tokens / cached_tokens / total_tokens`（`app/store.py:245-249`），单价侧也配了 `model_price_cached_per_million`（`app/config.py:66`）。**所以只缺聚合层，采集不用动。**

## 三、口径（已定 / 待定）

**已定：**

- **总 token = 历史累计**，不分时间窗 —— 沿用 `/admin/overview` 现有的求和逻辑。
- **平均每个规划的 token 要加**（新指标）。

**待定（实现前定一下就行）：平均的分母**
`total_tokens` 为 NULL 的运行算 0、还是排除？建议**排除**（只统计"有 token 快照的运行"），并在 hint 里如实写"N 个运行有 token 快照" —— 仓库里 `cost_known_runs` 已经是这个写法（`app/admin_analytics.py`），沿用能避免两处口径不一致。

**摆放建议（未确认）：**

- 总 token 是**历史量**，跟窗口 KPI 混在同一行会被误读成"同窗口" → 建议它**留在「累计用量」折叠卡**里，只是文案写清"历史累计"；
- 「平均每个规划的 token」放**顶部 KPI 行**，与「平均成本 / Run」并列（两者都按同一窗口算，并排不会混淆）。

## 四、顺带一句：token 指标只解释成本，不解释"慢"

慢的第一瓶颈仍是模型时延与 90s 单源超时（见 `docs/目前缺陷.md` C1 / C2）。KPI 行里已有「P95 规划耗时」和「平均成本 / Run」，token 加进去后三者各司其职，别混着读。
