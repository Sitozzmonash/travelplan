## 2. 逐个说明

### railway_12306（MCP，主源）

- 启动：`npx -y 12306-mcp`（可用 `RAILWAY_12306_COMMAND` 覆盖），走 stdio，由 SuperHarness 的
  MCP 装载器按需拉起，不常驻。
- 依赖：Node ≥ 18 与网络。**容器部署必须装 Node**（见 `Dockerfile`）。
- 失败表现：`UNAVAILABLE` / `TIMEOUT` / `INVALID_RESPONSE`；此时大交通自动落到途牛。
- 已知现象：12306 偶尔返回早一天的车次，planner 用 `departure_day_offset` 识别并
  生成 `OUTBOUND_OFF_DATE` 告警（不偷偷改用户给的日期）。

### tuniu_travel（Plugin）

- 依赖：`TUNIU_API_KEY` + `tuniu` CLI（`npm i -g tuniu-cli`；Windows 下自动解析 `tuniu.cmd`）。
  可用 `TUNIU_COMMAND` 覆盖命令。
- 未配置 `TUNIU_API_KEY` 时**不会启动子进程**，直接返回 `AUTH_ERROR`。
- 超时/非零退出码映射为 `TIMEOUT` / `UNAVAILABLE`。
- **只导出查询类工具**，下单/支付类工具刻意不暴露（V1 只读）。

### amap_cn（Plugin）

- 依赖：`AMAP_API_KEY`（只从环境变量读）。缺 Key 时**不发请求**，直接 `AUTH_ERROR`。
- 用途：`search_poi` / `poi_detail` / `geocode` / `route`。
- 路线失败时 planner 用**具名常量**做粗估（`DETOUR_FACTOR`、`SPEED_KMH`），
  并把 `TravelLeg.verified=False`，Critic 据此下调计划置信度 —— 不假装路线是真的。

### tikhub_social（Plugin，攻略主源）

- 依赖：`TIKHUB_API_TOKEN`。模块内 `FREE_ONLY` 是编译期常量：只允许免费额度。
- 先查额度（`free_credit`），额度不足直接 `FREE_CREDIT_EXHAUSTED`，**不动现金余额**；
  402 → 同样判为额度耗尽。
- 标注计费的端点不会被重试（避免重复计费）。

### mediacrawler_social（Plugin，攻略兜底）

- 依赖：本地克隆目录（默认 `data/vendors/MediaCrawler`，可用 `MEDIACRAWLER_DIR` 覆盖）。
- 目录不存在、未登录、触发风控、超时 → 一律返回空结果 + `UNAVAILABLE` / `TIMEOUT`，
  **绝不编造攻略内容**。

### LLM

- 配置：`MODEL_NAME` / `MODEL_BASE_URL` / `MODEL_API_KEY`；单次超时 `TRAVELPLAN_LLM_TIMEOUT_SECONDS`（默认 180 秒）。
  **但它不是唯一预算**：`llm_timeout_for_tag()`（`app/config.py:626-645`）按**用途**给更紧的预算 ——
  `extract_places` 120s（按**整批**给，不是按单篇）、`extract_places_retry` 45s、`critic` 90s、
  `final_answer` 120s，其余 tag 用基线 180s。这四个可分别用
  `LLM_TIMEOUT_EXTRACT_SECONDS` / `LLM_TIMEOUT_EXTRACT_RETRY_SECONDS` / `LLM_TIMEOUT_CRITIC_SECONDS` /
  `LLM_TIMEOUT_FINAL_SECONDS` 覆盖。
  基线超时有**两个**入口，别混淆：`TRAVELPLAN_LLM_TIMEOUT_SECONDS` 由 `app/llm.py` 直接读（调用方没显式传
  timeout 时生效，`app/llm.py:52`），`LLM_TIMEOUT_SECONDS` 进 `app/config.py` 的 `llm_timeout_seconds`，
  作为"按用途查表查不到"时的默认值。两者默认都是 180s。
  预算打满只是**如实降级**（`status=TIMEOUT` 落 Trace），不编造内容。
- `LLM_STAGE_MAP`（`app/workflow.py:4712-4718`）里只映射了 **5 个** tag：`parse_intent`、
  `query_expansion`、`extract_places`、`critic`、`final_answer` —— **照它抄必然漏**。
  按用途算是 **7 类**调用点，另有 1 个重试 tag：
  - `llm_ranking`：候选方案**软排序**（`app/decision/planner_decision.py:52`、`:201-202`，
    由 `app/workflow.py:3301` 作为 `llm_ranker` 注入）—— Jev 不可用/失败时的 LLM Ranking 兜底层；
  - `preference_profile`：**动态偏好画像**（`app/decision/profile.py:79`，
    由 `app/workflow.py:1534` 调用）；
  - `extract_places_retry`：地点抽取失败后的重试批次（`app/discovery.py:520`）。
  tag 定义见 `app/prompts.py`。
- 失败表现：`LLMResult.status != OK` → 该处降级到确定性的代码路径，并写入
  `audit_report.json` 的 `llm_calls` 与 `degradations`。**任何一处失败都不会让整次规划失败。**

### Jev

- 配置：见 [02_配置说明.md](02_配置说明.md)。
- 调用点只有三处（`app/decision/planner_decision.py`；同一文件里还有第 4 种决策记录
  `DECISION_LLM_RANKING`，但那条走 LLM 而非 Jev，见上一节）：
  - `plan_choice`：在 Top-K 候选中选一份（候选 < 2 时不发问，省一次调用）；
  - `tradeoff`：当前方案与其它候选的取舍，返回 `KEEP_A` ~ `KEEP_E` 或 `REPLAN`
    （`VARIANT_LABELS` 共 A~E 五个，`app/planner.py:2653-2659`；候选上限
    `MAX_PLAN_CANDIDATES=5`，`app/workflow.py:447`）。criteria **由实际候选动态生成**：
    每个候选一项 `KEEP_{label}` + 一个 `REPLAN`，候选少于 5 个时选项就相应变少
    （`app/decision/planner_decision.py:438-447`）；
  - `quality_gate`：`KEEP` / `REPLAN`，并回传 `pace_score` / `preference_match` /
    `diversity_score` / `confidence`。
- 失败语义：`TIMEOUT` / `UNAVAILABLE` / `SKIPPED` / `INVALID_REQUEST` / `INVALID_RESPONSE` /
  `LOW_CONFIDENCE` / `BUDGET_EXCEEDED`，以及非 200 时通用的 `HTTP_{status}`
  （如 `HTTP_429` / `HTTP_401` / `HTTP_403` / `HTTP_500`）→ 记 trace、标记 fallback、
  确定性路径继续。**Jev 永远不是单点故障。** 其中：
  - `UNAVAILABLE` = 网络类错误（`app/decision/jev.py:110-112`）；
  - `SKIPPED` = `JEV_ENABLED=false` / 未配 `JEV_API_KEY` / 熔断已打开（`:78`、`:80`、`:82`）；
  - `INVALID_REQUEST` = Choice 问题的选项少于两个（`:87`）。
- 熔断：超时、网络错误、鉴权/限流/5xx、结构不合法都会打开本 run 的 circuit breaker，
  后续调用直接 `SKIPPED`，不再浪费额度。触发条件是
  `status_code in {401, 403, 429} or status_code >= 500`（`app/decision/jev.py:115-117`）；
  其它 4xx（如 400 / 404）同样记成 `HTTP_<code>`（`:121`），但**不**打开熔断。
- 额度：只在响应里真的带了额度时才记录（`quota_source=reported`），否则 `unknown` ——
  **不伪造剩余额度**。

## 3. 发送给 Jev 的边界（硬规矩）

允许发送：

```text
旅行意图摘要（白名单字段：出发地/目的地/天数/日期/节奏/偏好/主题/预算/人数）
候选行程摘要（每天的区域、项数、活动分钟数、条目名/类型/时刻）
质量软分与代码判定的硬问题清单
```

**禁止发送**：API Key / Secret、来源 URL、原始 Provider 响应、完整 Trace、用户身份
（`user_id`）、原始 query 之外的隐私字段。

这条边界的实现方式是**白名单**而不是"排除若干字段"（`planner_decision.py:INTENT_ALLOWLIST`）：
以后 `TripIntent` 新增敏感字段时，默认不会外发。`tests/test_jev_integration.py`
会断言 Jev 收到的 state 里不含 `api_key` / `Bearer` / `user_id` 等字样。

## 4. 降级统一语义

`PROVIDER_STATUSES`（`app/providers.py:103-112`）**只有下面 8 个**；`BUDGET_EXCEEDED`
不在其中，它只是 **JevResult** 的状态（`app/decision/jev.py:85`）。

| 状态 | 含义 | 谁会产生 |
| --- | --- | --- |
| `OK` | 成功 | 全部 |
| `EMPTY` | 调用成功但没有数据 | 高德、途牛、TikHub |
| `UNAVAILABLE` | 服务不可用 / 未配置 / 依赖缺失 | 全部 |
| `TIMEOUT` | 超时 | 全部 |
| `AUTH_ERROR` | 缺 Key 或 Key 无效（**未发出请求**） | 途牛、高德、TikHub |
| `RATE_LIMIT` | 被限流 | 高德、TikHub |
| `FREE_CREDIT_EXHAUSTED` | 免费额度耗尽（不动现金） | TikHub |
| `INVALID_RESPONSE` | 返回结构不符合契约 | 12306 MCP、Jev、Plugin 工具 |
| `BUDGET_EXCEEDED` | 达到本次 run 的 Jev 调用上限（**不是 Provider 状态**） | 仅 Jev（`jev.py:85`） |

**已知缺口：TikHub 的 `SAFE_MODE_BLOCK`。** TikHub Plugin 在"无法证明这次调用不会先扣现金
余额"时会返回 `SAFE_MODE_BLOCK`
（`super_harness/superharness/capabilities/plugins/tikhub_social/tools/search.py:82`、`:300-310`），
但它不在 `PROVIDER_STATUSES` 里，经 `app/providers.py:316-325` 的 `_status_of()` 会被归一成
`EMPTY`；而 `EMPTY` 不在 `FALLBACK_STATUSES`（`app/providers.py:116-118`）。后果是这一路
**既不会显示为 `SAFE_MODE_BLOCK`、也不会 fallback 到 MediaCrawler** —— 观测上看起来像
"TikHub 搜了但没搜到"，与真实原因（安全模式拒发请求）不符。此处如实记录，尚未修复。

`INVALID_RESPONSE` 的产生方也不止 12306 MCP 与 Jev，Plugin 工具同样会产：
`app/providers.py:957-959`（工具返回无法解析为空 payload）、途牛
`tuniu_travel/tools/flight.py:253`、TikHub `tikhub_social/tools/search.py:284-289`。

三条铁律：

1. **失败也要留痕**。"查了但没查到"与"根本没查"是两件事：失败的调用同样写进
   调用账本（`provider_calls` 表 + `audit_report.json:provider_calls`，`status != OK` + note）。
2. **绝不用假数据兜底**。没有真实价格/时刻/路线时，宁可缺失、宁可告警，
   也不生成一个"看起来合理"的数字。
3. **凭据不进账本**。调用参数里的 `api_key/token/authorization/secret` 在存储边界
   （`store._scrub_query`）被替换成 `***`，任何接口不回显明文。

## 5. Provider 调用账本与健康观测

`app/providers.py:ProviderHub` 的调用账本（`audit_entries()`）之外，还有一张**观测用**的
SQLite 表 `provider_calls`（`app/store.py`），它不带 `runs` 外键。原因：引导式旅程的
Discovery 调用发生在 Planning Session 里，那时还没有正式 run；写 `sources` 会撞外键或污染
运行列表。

```text
sources        = 这次 run 用了什么证据（业务，带外键）
provider_calls = 谁在什么时候调了哪个数据源、成不成、多快（观测，无外键）
```

写入方两处：

| 写入方 | `source_type` | 场景 |
| --- | --- | --- |
| `app/sessions.py:_record_provider_calls` | `discovery` | 会话 Prefetch（无 run_id） |
| `app/workflow.py:_record_provider_calls`（`node_finalize`） | `run` / `benchmark` | 正式 run 与 Benchmark 用例 |

`benchmark` 这一支**是可达的**：`benchmark/runner.py:118-120` 显式传 `source="benchmark"`，
`app/workflow.py:4776-4777` 据此写 `source_type="benchmark"`；CLI 走 `main.py:70` 的
`source="cli"`，归入 `run`。

`sources` 表还有第三种来源：**城市知识库复用的攻略正文**。跨会话复用正文时本次并没有出网，
所以这些行由 `app/workflow.py:_materialize_city_evidence` 写成 `status="CACHED"`
（`STATUS_CACHED`，**不属于**上面的 `PROVIDER_STATUSES` 词表），`fetched_at` 保留**原始抓取时间**，
`normalized_json` 带 `{origin: "city_cache", city_cache_updated_at: ...}`，并按
`{run_id}-cache-{n}` 重新分配 source_id（`sources.source_id` / `evidence.evidence_id` 都是全局主键，
沿用上一次会话的 id 会把上一轮 run 的归属改掉）。它们**不写进 `provider_calls`**，
因此不会污染 Provider Health 的调用统计。

`GET /api/v1/admin/providers` 用 `store.provider_call_stats(limit_per_provider=200)` 聚合每
Provider **最近 N 次真实调用**，给出 status / 成功率 / 失败率 / timeout / fallback / 平均与 P95
延迟 / tools / sources / configured；**没有历史 = UNKNOWN 而不是失败**，且不主动打第三方接口
（不做假探活）。完整口径见 [12_Provider健康与观测.md](12_Provider健康与观测.md)。

`source_type` 实际有三种取值 —— `discovery`（会话 Prefetch）、`run`（正式 run，含 CLI 的
`source="cli"`）、`benchmark`（Benchmark 用例），因此能回答"某个 Provider 在正式 Run 正常、
但 Discovery 阶段大量超时"这类问题。
