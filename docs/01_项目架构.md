# 01 项目架构

一句话：这份文档说明 TravelPlan 由哪几层组成、每层的边界在哪、一次请求的数据怎么流动。

## 1. 顶层目录

```text
travelplan/
├─ app/                     业务代码（Python）
│  ├─ api.py                FastAPI 层：HTTP 形状 ↔ RunResult（ASGI 变量名 api）
│  ├─ agent.py              装配：把 super_harness 的 runtime 与旅行业务接起来
│  ├─ sessions.py           Planning Session：引导式旅程的"规划前会话"状态机 + Prefetch
│  ├─ city_cache.py         跨会话「城市知识库」：攻略 + 高德 POI 的半静态缓存（按城市分片）
│  ├─ discovery.py          取数逻辑的**唯一实现**（Prefetch 与 Workflow 节点共用）
│  ├─ selection.py          用户选择层：策略→权重、Pace auto、MUST/WANT/REJECT
│  ├─ workflow.py           固定 12 步 LangGraph 流程 + 产物写出 + 运行入口
│  ├─ planner.py            旅行领域算法（纯函数、无网络、无随机）

│  ├─ llm.py                模型调用与降级
│  ├─ models.py             Pydantic 领域模型
│  ├─ store.py              证据库（SQLite / Postgres 双后端，含 Session / 城市缓存 / Provider 账本 / RuntimeConfig 等表）
│  ├─ db.py                 后端选择与 SQLite→Postgres 方言翻译
│  ├─ observability.py      Run/Span 状态与 span 分类
│  ├─ badcase.py            Bad Case 规则引擎
│  ├─ evolution.py          Evolution：Bad Case → 经验
│  ├─ config.py             集中配置与可调阈值
│  ├─ version.py            版本信息（Trace / Baseline 都要记是哪一版跑的）
│  └─ decision/
│     ├─ jev.py             Jev 调用适配层（超时/额度/熔断/降级）
│     ├─ profile.py         动态偏好画像（Dynamic Preference Profile）生成
│     └─ planner_decision.py 三个软决策节点：方案选择 / Trade-off / 质量门（+ LLM Ranking 兜底）
├─ benchmark/               评测套件（确定性套件离线可复现；另有 5 例联网 Live Smoke）→ 见 07
├─ frontend/                Next.js App Router：用户端 + 管理端
├─ super_harness/           git submodule：Runtime / Tool / MCP / Model / Trace

├─ docs/                    本文档
├─ main.py                  本地 CLI
├─ Dockerfile               API 容器镜像（含 Node，供 12306 MCP）
└─ requirements.txt
```

## 2. 分层与边界

```text
┌──────────────────────────────────────────────┐
│ 展示层  frontend/（用户端 + 管理端）           │  只做展示，不含业务判断，不持有任何 Secret
├──────────────────────────────────────────────┤
│ HTTP 层 app/api.py                            │  只做翻译：HTTP 形状 ↔ RunResult / 库里的事实
├──────────────────────────────────────────────┤
│ 准备层 app/sessions.py + app/discovery.py      │  引导式旅程：会话状态机 + 后台 Prefetch（取数唯一实现）
├──────────────────────────────────────────────┤
│ 流程层 app/workflow.py                        │  只负责"按固定顺序走 12 步"
├──────────────────────────────────────────────┤
│ 领域层 app/planner.py + app/selection.py       │  纯函数：算分、排程、预算、约束、质量度量、用户选择
├──────────────────────────────────────────────┤
│ 决策层 app/decision/                          │  Jev：只在可枚举选项之间做软决策
├──────────────────────────────────────────────┤
│ 能力层 app/providers.py + super_harness/       │  真实价格/车次/路线/攻略从哪来
├──────────────────────────────────────────────┤
│ 持久层 app/store.py                           │  每次 run 的证据、决策、度量、BadCase、Session、Provider 账本
└──────────────────────────────────────────────┘
```

五条不能越界的规则：

1. **HTTP 层不许算东西**。`api.py` 不比较价格、不排行程；它只把 `RunResult` 与库里的行
   翻译成 JSON。任何"顺手算一下"都会让 CLI 与 Web 走两套逻辑。
2. **取数只有一份**。查交通/酒店/攻略/地点的实现在 `app/discovery.py`，Session Prefetch
   与 Workflow 节点共用；不允许"Web 一套、Workflow 一套"。
3. **流程层不许改数字**。`workflow.py` 的节点只做三件事：调用领域算法 / 调用能力层 /
   写 state。它不发明价格、不改时间。
4. **领域层不许联网、不许调模型**。`planner.py` 里没有任何 HTTP 与 LLM 调用，所以它可以
   脱网单测（`tests/test_planner.py` 240 条，1.7 秒跑完）；`selection.py` 是纯函数式的
   用户选择层，同样不联网。
5. **软决策不许越过硬约束**。Jev 的选择必须再过一次
   `planner.hard_constraint_violations()`，不通过就退回默认方案（见 04 与
   `app/decision/planner_decision.py:choose_plan`）。用户点的 REJECT 同理：在候选打分前
   就被硬排除（`selection.apply_user_place_preferences`）。

## 3. 一次请求的数据流

两条入口汇聚到同一个执行体：

```text
Quick（一句话 / CLI）
用户（前端 / CLI / HTTP）
  → POST /api/v1/plans {message, background:true}
  → api.create_plan()：建 run 行（status=RUNNING）→ 线程池执行 run_travel
  → app.agent.run_travel（唯一业务入口）
  → app.workflow.execute_travel_run

Guided（引导式）
用户（前端向导）
  → POST /api/v1/planning-sessions        （建会话 + 后台 Discovery/Prefetch）
  → PATCH /api/v1/planning-sessions/{id}  （改偏好/POI，只重排序）
  → POST /api/v1/planning-sessions/{id}/start
  → app.sessions.start_run()：建 run 行（source=guided）→ 线程池执行 _start_job
  → app.workflow.execute_travel_run(intent=..., prefetch=..., source="guided")

执行体（两条入口共用）
  → app.workflow.execute_travel_run
       ① 建 state（store / hub / llm / jev / record_span / progress_hook / intent / prefetch）
       ② travel_graph().invoke(state)  ← 12 步，每步前后写进度与 span
       ③ persist_metrics()：汇总 token / 调用次数 / BadCase 数 → run_metrics 表
       ④ 写 outputs/<run_id>/ 下的六件产物，**分两步**：
          _write_artifacts()（finalize 内，app/workflow.py:4359）
              → plan.json / plan.md / audit_report.json
          _write_run_artifacts()（整张图跑完之后，app/workflow.py:4619）
              → trace.jsonl / metrics.json / badcases.json，
                并回填 audit_report.json 的 artifacts 索引
          （后三件必须等图跑完：finalize 执行时它自己的 span 与 run_metrics 都还没落库）
  → RunResult 落库并返回
用户侧轮询 GET /api/v1/plans/{run_id}/status（真实阶段状态）
用户侧读取 GET /api/v1/plans/{run_id}（plan + evidence）与 /audit（规划依据）
管理端读取 /api/v1/admin/runs/{run_id}（trace / jev_calls / llm_calls / badcases / user_journey）
```

一次 run 的副作用清单（都可以事后查证）：

| 落点 | 内容 |
| --- | --- |
| `data/travelplan.db` | 共 25 张表（以 `app/store.py` 的 `CREATE TABLE IF NOT EXISTS` 为准）：runs / trip_requests / sources / evidence / places / place_evidence / decisions / plans / plan_items / run_progress / run_stages / trace_spans / run_metrics / badcases / benchmark_runs / benchmark_case_results / evolution_runs / experiences / planning_sessions / city_pois / city_poi_mentions / city_evidences / city_cache_meta / provider_calls / runtime_config |
| `outputs/<run_id>/` | plan.json、plan.md、audit_report.json、trace.jsonl、metrics.json、badcases.json |
| stdout（SuperHarness） | 结构化运行日志（模型、工具调用、决策） |

`planning_sessions` 存引导式会话（含 `discovery_json` / `prefetch_json` / `events_json`），
`provider_calls` 是 Provider 调用账本（观测，无 runs 外键），`runtime_config` 是管理端可运行时
修改的非 Secret 配置；`city_pois` / `city_poi_mentions` / `city_evidences` / `city_cache_meta`
是目的地级共享的「城市知识库」（`app/city_cache.py` 写入并读取，**跨用户、跨会话**按城市分片复用，
含 POI、攻略提及、**攻略正文**与检索词，见 [13](13_数据流与复用机制.md)）。
这几类都不属于"一次 run 的证据"，
见 [11](11_用户旅程与PlanningSession.md) 与 [12](12_Provider健康与观测.md)。

## 4. 为什么用 LangGraph 的固定图，而不是一个大函数

`app/workflow.py` 把流程拆成 12 个节点，每个节点只往 state 写自己负责的键。原因是
**审计要能回答 12 个问题**（第 5 步抽了哪些地点、第 6 步哪些路线没核实、第 11 步 Critic 说了
什么……）。拆成节点后，这 12 个答案就是 state 的 12 个键，不必从日志反推；副作用是每步
都能单独单测。

图不带 checkpointer（固定流程天生可重放），因此 state 里可以放 `store` / `hub` / `llm` /
`jev` 这类句柄。真要加断点续跑时，这几个键必须换成可重建的轻量标识 —— 这是唯一的约束。

## 5. 与 SuperHarness 的边界

| 谁 | 负责 |
| --- | --- |
| SuperHarness（submodule） | Runtime、Tool/MCP 装载、模型接入、重试、EventBus/Trace 基础设施、5 个能力插件 |
| TravelPlan（本仓） | 旅行领域算法、固定流程、证据库、BadCase/Evolution、评测、前端 |

本仓**不自制** Router / Plugin Loader / MCP Client / Memory / RAG / Retry，一律复用
SuperHarness；只在它之上补业务级的事实（进度、span、BadCase）。
详细的能力清单见 [04_数据源与工具.md](04_数据源与工具.md)。
