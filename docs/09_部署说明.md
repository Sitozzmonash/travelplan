# 09 部署说明

一句话：前端可以放 Vercel，**后端 API 不行** —— 这篇说明为什么、以及推荐怎么放。

结论先给：

```text
推荐形态：Vercel（Next.js 前端） + 一个常驻容器（FastAPI + SQLite 卷 + Node）
同域名：用 Vercel rewrites 把 /api/* 反代到容器，或容器侧反代前端
```

## 1. 为什么 API 不能放在 Vercel 的 Serverless 上

以下每条都对应一个具体的代码事实，不是"性能担忧"。Vercel 的限制数字取自官方文档
（[Functions Limits](https://vercel.com/docs/functions/limitations)，最后更新 2026-08-24）。

| # | 代码事实 | 与 Vercel 的冲突 |
| --- | --- | --- |
| 1 | 一次真实规划**实测 616 秒**（10 分 16 秒，见下"实测记录"） | 函数最长执行时间：Hobby **300s**、Pro 默认 300s / 上限 **800s**（1800s 为 beta）。Hobby 必然 504；Pro 也只剩不到 3 分钟余量 |
| 2 | `background:true` 用**进程内** `ThreadPoolExecutor`（`app/api.py:_RUN_EXECUTOR`） | 响应返回后实例会被冻结/回收，后台 run 不保证继续跑 → 会出现永远停在 `RUNNING` 的记录。轮询模型假设"服务端进程一直活着" |
| 3 | 数据落在 SQLite（`data/travelplan.db`，20 张表） | Serverless 只有 `/tmp` 可写且实例之间不共享；`runs`/`trace_spans`/`badcases`/`benchmark_runs`/`evolution_runs` 全部无法持久化 |
| 4 | 产物写 `outputs/<run_id>/`（六件文件） | 同上：函数文件系统只读，产物需要对象存储 |
| 5 | 12306 走 MCP **stdio**（`npx -y 12306-mcp`，`app/providers.py:default_mcp_servers`） | 需要 Node 运行时 + 长驻子进程 + 首次 `npx` 下载；Vercel 的 Python 函数镜像里没有 Node，也不能长期持有子进程 |
| 6 | MediaCrawler 需要本地克隆目录 + 已登录浏览器会话 | 只读文件系统 + 无持久进程 + 无浏览器会话，**不可能** |

反过来，以下能力在 Vercel 上是没问题的（纯 HTTP 出站）：途牛、高德、TikHub、LLM、Jev，
以及管理端的环境变量鉴权。

## 2. 推荐方案（少服务、但不用"强行一套"）

```text
┌──────────────────────────┐        ┌────────────────────────────────────┐
│ Vercel                   │        │ 常驻容器（Railway / Fly.io / Render │
│  Next.js 前端            │  /api/* │ / 任意 VPS）                        │
│  /admin 管理端           │ ─────► │  uvicorn app.api:api               │
│  NEXT_PUBLIC_API_BASE_URL│        │  SQLite 挂卷（TRAVELPLAN_DB_PATH）  │
└──────────────────────────┘        │  Node（供 12306 MCP）               │
                                    │  MediaCrawler 目录（可选）          │
                                    └────────────────────────────────────┘
```

容器镜像已提供：`Dockerfile`（`python:3.12-slim` + `nodejs`/`npm`，挂载 `/data`）。

```bash
docker build -t travelplan-api .
docker run -d --name travelplan-api -p 8000:8000 \
  -v travelplan-data:/data \
  -e TRAVELPLAN_DB_PATH=/data/travelplan.db \
  -e TRAVELPLAN_OUTPUT_DIR=/data/outputs \
  -e MODEL_NAME=... -e MODEL_BASE_URL=... -e MODEL_API_KEY=... \
  -e AMAP_API_KEY=... -e TIKHUB_API_TOKEN=... -e TUNIU_API_KEY=... \
  -e JEV_API_KEY=... -e TRAVELPLAN_ADMIN_TOKEN=... \
  travelplan-api
```

**必须挂在卷上的两样东西**：`TRAVELPLAN_DB_PATH` 与 `TRAVELPLAN_OUTPUT_DIR`。
不设这两个变量时它们会落在镜像层里，重新部署一次历史就没了（这也是它们默认值之外
额外提供环境变量的原因）。

单 worker 运行（`Dockerfile` 的 CMD 就是单 worker）：SQLite 与进程内 Run 执行器都是
单机语义，多 worker 会让轮询读到另一个实例的库。要并发就多开容器 + 外部数据库。

## 3. 前端放 Vercel

```text
1) Vercel 新建项目 → 选这个 GitHub 仓库
2) Root Directory 设成 frontend/
3) 环境变量：NEXT_PUBLIC_API_BASE_URL = https://<你的 API 域名>
4) 部署（Next.js 会被自动识别）
```

同域名的两种做法：

- **Vercel rewrites**：在 Vercel 项目里加一条 rewrite，把 `/api/*` 转发到容器域名，
  前端就用同域相对路径请求（`NEXT_PUBLIC_API_BASE_URL=""`）。注意管理端用的是
  `Authorization` 头，rewrite 不会丢头。
- **容器侧反代**：把 `frontend/` 的构建产物一起打进容器，由容器（nginx / Caddy）统一对外。

`NEXT_PUBLIC_*` 是**编译期内联**的，改了要重新部署；管理端 Token 不放这里（见 02）。

## 4. 如果一定要"一个 Vercel 项目"

Vercel 支持把 Python 后端与前端放在同一个项目（Vercel Services），但需要先改造：

| 改造项 | 具体做法 | 代价 |
| --- | --- | --- |
| 数据库 | SQLite → 托管 Postgres（Neon / Vercel Postgres），`app/store.py` 换成 psycopg 实现 | 约 700 行 store 需要移植；事务/并发语义要重测 |
| 产物 | 本地文件 → Vercel Blob / S3 | 产物下载接口要改；审计链路要重新验证 |
| 长任务 | 进程内线程池 → Vercel Workflows（或 Pro 的 800s + 前端轮询） | 主流程要改成可暂停/可恢复，改动面大 |
| 12306 | 无法运行 MCP stdio | 要么放弃 12306（大交通只剩途牛），要么自建一个外部 12306 服务 |
| MediaCrawler | 无法运行 | 放弃（攻略只剩 TikHub） |
| Python 入口 | 需要显式声明 `app.api:api`（Vercel 默认查找 `app.py`/`main.py` 等，本仓 `main.py` 是 CLI，不含 ASGI 变量） | 加 `pyproject.toml` 的 `[tool.vercel] entrypoint = "app.api:api"` |

也就是说：**一条 Vercel 项目能实现，但要以"丢掉 12306 + 换掉数据库"为前提。**
按"稳定性高于强行一套服务"的原则，推荐第 2 节的形态。

## 5. 环境变量清单（部署时）

后端（容器）：`MODEL_NAME`、`MODEL_BASE_URL`、`MODEL_API_KEY`、`AMAP_API_KEY`、
`TIKHUB_API_TOKEN`、`TUNIU_API_KEY`、`TAVILY_API_KEY`、`JEV_API_KEY`、
`TRAVELPLAN_ADMIN_TOKEN`、`TRAVELPLAN_DB_PATH`、`TRAVELPLAN_OUTPUT_DIR`、
`TRAVELPLAN_CORS_ORIGINS`；可选 `RAILWAY_12306_COMMAND`、`TUNIU_COMMAND`、
`MEDIACRAWLER_DIR`、`TRAVELPLAN_COMMIT`。

前端（Vercel）：`NEXT_PUBLIC_API_BASE_URL`；可选 `NEXT_PUBLIC_USE_MOCK_API=false`。

安全默认值：**不配 `TRAVELPLAN_ADMIN_TOKEN` 时所有 `/api/v1/admin/**` 返回 503**，
Trace / Config / Evolution 不会因为"忘了配"而公开。

## 6. 实测记录（本次验证做了什么、没做什么）

已验证：

| 项 | 证据 |
| --- | --- |
| 前端生产构建 | `cd frontend && npm run build` 退出码 0（Next.js 16 / React 19） |
| ASGI 应用可跑 | `uvicorn app.api:api` 启动，`/api/v1/health` 返回 `status=ok` |
| 真实端到端一次规划 | run `tp-20260920-164133-9291f8`：status=`DEGRADED`（成功产出），**616 秒**，36968 tokens，8 次模型调用，**3 次真实 Jev 调用**，48 次工具调用，12 个阶段全部走完 |
| 12306 MCP stdio 可用 | 同一次 run 的日志：`12306 MCP Server running on stdio`，`railway_12306_get-tickets` 返回 10 条（13.9s） |
| Trace 覆盖 | 同一次 run 的 span 分类：`workflow 12 / mcp 1 / provider 5 / tool 13 / planner 2 / jev 3 / budget 1 / feasibility 1 / critic 1 / llm 8 / store 1`（11 类全覆盖） |
| 容器镜像可构建、可运行 | `docker build` 成功；容器内 `/api/v1/health` 返回 ok，`node v20.19.2`/`npx 9.2.0` 可用，`/data` 可写并建出全表 |
| 数据库路径可挂卷 | `TRAVELPLAN_DB_PATH` 生效（容器内 `/api/v1/health` 的 `store.path` 指向卷内路径） |

**未验证**：没有真的往 Vercel 部署（需要在你的账号下新建项目，且本仓 API 客观上跑不了
Serverless）。上面所有"Vercel 跑不了"的结论来自**代码事实 + 官方文档数字**的组合，
不是猜测；如果你想动手验证，最小实验是：把 `frontend/` 单独部署到 Vercel，然后观察
一个长任务请求是否 504 —— 预期 Hobby 会在 300 秒被掐断。
