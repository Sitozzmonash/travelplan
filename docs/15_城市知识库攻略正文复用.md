# 15 城市知识库：攻略正文的跨会话复用

> **一句话**：城市知识库原来只缓了"高德 POI + 攻略提及"，**没缓攻略正文**，于是第二个去同一座城市的
> 会话仍然要把社媒检索 + 模型抽取全价重付一遍 —— 缓存只解决了一半。本文记录这个问题的描述、
> 建议方案、实际实现与当前状态。
>
> **状态**：✅ 已实现、已测（全量 `1003 passed`）、**尚未 commit**（按本仓约定由用户统一提交）。
> 2026-09-21 追加 §9「预热脚本」：读路径已通，但填充原来只能"等第一个用户来踩"，补上离线预热。
>
> **相关文档**：[13_数据流与复用机制.md](13_数据流与复用机制.md) §2.1（机制描述）、
> [目前缺陷.md](目前缺陷.md) 的 A1 / A3 条目（台账状态）。

## 1. 问题：命中缓存了，为什么攻略还要重抓？

### 1.1 现场

```
会话 1：北京 → 成都，3 天        ← 冷启动，成都知识库为空
会话 2：广州 → 成都，5 天        ← 命中成都知识库
```

按当时的设计，会话 2 应该"复用成都的半静态数据"。实际表现是：

| 数据 | 会话 2 是否复用 | 为什么 |
| --- | --- | --- |
| 高德 POI（名称/坐标/营业时间/地址） | ✅ 复用 | 存在 `city_pois`，命中后一次 `search_poi` 都不打 |
| 攻略**提及**（哪篇攻略提到哪个点，500 字片段） | ✅ 复用 | 存在 `city_poi_mentions` |
| **攻略正文** | ❌ **重新抓** | **没有任何地方存过它** |
| **检索词计划**（`social_queries`） | ❌ **重新算** | 只活在会话 JSON 里 |
| 车次 / 航班 / 酒店价格 | ❌ 重新查 | 实时数据，本来就不该缓存（这条是对的） |

也就是说：**最便宜的那部分（POI）复用了，最贵的那部分（社媒检索 + 模型抽取）没有。**

### 1.2 代价

重抓攻略是整条链路最贵的一段：

```
query_expansion（LLM 扩写检索词）          实测 ≈ 13.5s
TikHub 社媒检索                            预算 45s
  └─ 失败退 MediaCrawler                   预算 180s
Tavily web_search                          独立一条
LLM 批抽取地点（正文是新抓的，必须重抽）    实测一批可到 54.7s
```

连带后果：

- **配额**：TikHub 免费额度被同一座城市反复消耗，实测多次 `RATE_LIMIT` / `FREE_CREDIT_EXHAUSTED`
  （这正是 `docs/目前缺陷.md` A1 记的限流根因之一）；
- **一致性**：两批结果不同，同一个用户两次问"成都有什么好玩的"会拿到不同候选；
- **体感**：用户被告知"数据来自 X 天前整理的攻略库"，实际攻略是刚抓的、POI 是旧的 —— 披露与事实不符。

## 2. 根因：三层断点，缺一层都修不好

```
会话 1 抓到攻略（Evidence：title + 全文 text + place_mentions + raw_metrics）
   │
   │  ① 落库时就丢掉了正文
   ▼
city_cache.write_candidates("成都", places, evidences)
   └─ _mention_rows() 只遍历 evidence.place_mentions，
      且要求"这个 mention 能按名字匹配上一个已核实的高德 POI"才写一行：
        city_poi_mentions(raw_name, source_type, provider, source_url,
                          snippet = evidence.text[:500],      ← 只截 500 字
                          tone, published_at, updated_at)
   → evidence 表本身不进城市缓存
   → 没有 place_mentions 的攻略（Tavily 网页、泛泛的"成都攻略"）一行都不写
   → 提到但没核实成 POI 的地名，也丢
   → 检索词（social_queries）没有任何落点

   │  ② 读出来也没送进 PrefetchBundle
   ▼
city_cache.read_candidates("成都") → CityCacheHit(places, mentions)
   sessions._prefetch_with_city_cache():
     social = SimpleNamespace(evidences=[], queries=[], served_queries=[])   ← 空的
     places = SimpleNamespace(places=cached.places)                          ← 用了
   cached.mentions 唯一的用处：给 social 阶段填一个 result_count
   PrefetchBundle 里根本没有装 mentions 的字段

   │  ③ 正式 Run 压根读不到城市缓存
   ▼
grep city_cache app/workflow.py  →  0 命中
   Run 只拿到 PrefetchBundle。即使缓存里躺着正文，它也没有句柄去读。

最终：node_search_social 的复用条件是
   bundle.evidences 非空  或  bundle.social_queries 非空
两者都是空 ⇒ 走全量分支：query_expansion(LLM) → 小红书/抖音/Tavily → 还得再抽一次地点
```

### 2.1 关键代码证据

| 断点 | 位置 | 事实 |
| --- | --- | --- |
| ① | `app/city_cache.py::_mention_rows` | 只从 `evidence.place_mentions` 生成提及行；`snippet = evidence.text[:500]` |
| ① | `app/store.py` 的 `city_pois` / `city_poi_mentions` DDL | 只有 POI 与提及，没有正文表 |
| ② | `app/sessions.py::_prefetch_with_city_cache` | `social = SimpleNamespace(evidences=[], queries=[], served_queries=[], ...)` |
| ② | `app/sessions.py` 的 `cached.mentions` 用法 | 全仓只有一处：给 social 阶段填 `result_count` |
| ③ | `app/workflow.py` | `city_cache` 零命中 |
| ③ | `app/workflow.py::node_search_social` | 复用条件只看 `bundle.evidences` 与 `bundle.social_queries` |

## 3. 为什么这不是"有意的设计取舍"

有三条独立证据说明它是**未做完**，而不是刻意只缓 POI：

1. **`write_candidates` 的签名本来就收 `evidences`。** 如果设计意图只是记"提及"，没必要把整包
   Evidence 传进来；它本来就是打算用这些证据的，最后只用了 `place_mentions` 这一小部分。

2. **`city_poi_mentions` 存的字段组合，恰好是"重建一条 source 所需的全部字段"**：
   `source_type / provider / source_url / published_at / snippet`，正是往 run 级
   `sources` + `evidence` 表插一行所需要的东西 —— 说明当初就准备过"从缓存重建证据"，只是没接上。

3. **`docs/目前缺陷.md` A3 自己写了方向**：
   > "把里面**半静态的那部分（evidences、places、social_queries）**的副产品落进 A1 的两张共享表"

   `evidences` 与 `social_queries` 都在方向里，实现的却只有 `places` 的全部 + `evidences` 的副产品。

### 3.1 顺便澄清一个常见的反驳

| 顾虑 | 为什么不成立 |
| --- | --- |
| "run 级证据必须绑 `run_id`（`evidence` / `sources` 有外键）" | 确实。但这不等于"必须重抓" —— 可以**从缓存复制正文**再插一条新的 run 级记录。而且 `_adopt_prefetch_sources` 那套"用原 source_id 过户"的机制已经存在（同会话 Discovery→Run 就靠它保住证据链） |
| "攻略有时效性，可能过期" | 已经用 TTL 表过态了：Hub 内 `social=6h`、城市缓存"攻略 15 天"。**接受了"TTL 内的攻略可复用"这个前提，却不复用正文，逻辑不闭环** |
| "复用正文会丢 provenance" | 不会，但要**重新分配 id**（见 §6.4）：沿用旧 id 才会把上一轮 run 的归属改掉 |

## 4. 建议的优化解决方案

### 4.1 目标与必须守住的不变量

**目标**：让第二个去同一座城市的会话，**一个社媒 Provider 都不打、一次地点抽取模型都不调**，
同时证据链与真实价格披露一样都不能坏。

**不变量（缺一个都不能算修好）**：

1. 机酒火价格 / 时刻表**永远不进**城市缓存（实时数据）；
2. 复用的证据必须能在本次 run 的 `sources` / `evidence` 里查到，`行程项 → 地点 → 证据 → 来源`
   这条链不断；
3. 复用的**事实**要如实披露（这是"来自 N 天前的缓存"，不是"刚查的"）；
4. 复用的正文不得污染 Provider Health 的调用统计（它统计的是"谁真的被调了"）；
5. 一座城市不会因为"只增不删"而**永远 stale**。

### 4.2 四处改动（按依赖顺序）

```
① 扩表：把攻略正文落进城市缓存
   新增 city_evidences(city, evidence_key, source_type, provider, source_url,
                        title, author, published_at, fetched_at, text,
                        place_mentions_json, specific_dishes_json,
                        raw_metrics_json, updated_at)   PK(city, evidence_key)
   新增 city_cache_meta(city, social_queries_json, social_served_queries_json, updated_at)
   evidence_key = sha1(source_url + title) 的内容键（**不是** run 级 evidence_id）

② city_cache 读写正文与检索词
   CityCacheHit 增加 evidences / social_queries / social_served_queries
   read_candidates 读正文（参与 TTL 判定 + 条数上限）
   write_candidates 写正文与检索词，并清理超期行

③ sessions 把它装进 PrefetchBundle
   _prefetch_with_city_cache 的 social 段不再留空
   → node_search_social 的第一个复用条件（bundle.evidences 非空）自然命中
   → node_extract_places 的 _discovery_already_extracted 也随之命中（同一批证据 id）
   → 检索词一起复用，连 query_expansion 那次模型调用也省掉

④ 正式 Run 重建 run 级 provenance（**必须在跑图之前**）
   sources.source_id 与 evidence.evidence_id 都是全局主键，
   sources 行不存在时 evidence 插入会被 PRAGMA foreign_keys=ON 拒掉
   → 新增 _materialize_city_evidence()：重新分配 {run_id}-cache-{n}，
     写 sources(status=CACHED, 原始 fetched_at, normalized_json={origin: city_cache})
```

### 4.3 关键设计取舍

| 决策点 | 选择 | 为什么不选另一个 |
| --- | --- | --- |
| 正文存哪 | 新建 `city_evidences` 表 | 加到 `city_poi_mentions` 会让同一篇文章的正文按"提及了几个地点"重复存 N 份 |
| 行的键 | `sha1(source_url + title)` | 用 run 级 `evidence_id`（形如 `{source_id}-e0`，内嵌 session_id）跨会话必然不同，会为同一篇文章反复累积新行；**只按 URL** 又会丢证据（搜索引擎对多个 query 返回同一 URL、标题不同） |
| 复用时 id 怎么办 | **重新分配** run 级 id | 沿用原 id 会把上一次 run 的 `sources` 行 `INSERT OR REPLACE` 成本次 run 的 —— 上一轮证据链当场断掉。（同会话 Discovery→Run 能沿用，是因为会话与 run 一一对应，跨会话不成立） |
| 复用证据算不算 Provider 调用 | **不算**，只写 `sources`，不写 `provider_calls` | 写进去会让 Provider Health 的调用次数 / 成功率 / P95 延迟被"凭空多出来的调用"污染，而它本来的用途正是回答"某 Provider 到底稳不稳" |
| 超期行 | 每次写入顺手清理 | 新鲜度口径是"**所有**行都在 TTL 内"，只增不删的话，一条再也搜不到的旧攻略会让这座城市**永远 stale**，于是每个新会话都触发一次后台全量刷新，TTL 名存实亡 |
| 公开只读接口 | 不外发正文，只给元信息 + 字符数 | `GET /api/v1/city-cache/{city}` **不需要鉴权**，且 40 条正文可达数百 KB |
| 检索词要不要一起缓存 | 要 | 省掉的那次 `query_expansion` 实测 ≈ 13.5s，与正文是同一批产物，不做白不做 |

## 5. 实施过程中自己踩的两个坑（都被自己的测试抓出来）

### 5.1 只按 URL 做内容键 → 丢证据

第一版 `_evidence_key` 用 `sha1(source_url)`。测试 `test_evidence_text_and_queries_roundtrip` 立刻报：

```
assert 3 == 6      # 缓存里只剩 3 条，实际抓了 6 条
```

原因：`FakeHub`（以及真实搜索引擎）对**多个 query 会返回同一个 URL**，标题与正文却不同。
按 URL 去重就把 3 条证据合并掉了。改成 `sha1(source_url + title)`：同篇文章重抓仍落同一行，
同 URL 的不同条目各占一行。

> 这条不是测试写得太严：丢证据 = Trust 的"多来源证据覆盖"分项被压低 = 用户看到"只有 1 条攻略支撑"，
> 属于**静默降质**，比慢更糟。

### 5.2 公开只读接口会外发全文

加了正文之后，`GET /api/v1/city-cache/{city}` 这个**无鉴权**接口会把最多 40 篇攻略全文吐给任何调用方。
给 `CityCacheHit.payload()` 加了 `include_evidence_text: bool = True`，接口传 `False`
（只给 `title / provider / source_url / published_at / chars`）。

## 6. 实际实现（逐处）

### 6.1 `app/store.py`

新增两张表（**每一列都写了显式类型** —— Postgres 不允许省略类型，而且报错发生在
`IF NOT EXISTS` 判断**之前**，`docs/09_部署说明.md` §2.3 记过这个坑）：

```sql
CREATE TABLE IF NOT EXISTS city_evidences (
    city TEXT NOT NULL,
    evidence_key TEXT NOT NULL,
    source_type TEXT NOT NULL,
    provider TEXT, source_url TEXT, title TEXT, author TEXT,
    published_at TEXT, fetched_at TEXT,
    text TEXT NOT NULL DEFAULT '',
    place_mentions_json TEXT NOT NULL DEFAULT '[]',
    specific_dishes_json TEXT NOT NULL DEFAULT '[]',
    raw_metrics_json TEXT NOT NULL DEFAULT '{}',
    updated_at TEXT NOT NULL,
    PRIMARY KEY(city, evidence_key)
);

CREATE TABLE IF NOT EXISTS city_cache_meta (
    city TEXT PRIMARY KEY,
    social_queries_json TEXT NOT NULL DEFAULT '[]',
    social_served_queries_json TEXT NOT NULL DEFAULT '[]',
    updated_at TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_city_evidences_updated ON city_evidences(city, updated_at);
```

新增方法（都沿用既有 `upsert_city_pois` 的写法：`INSERT ... ON CONFLICT ... DO UPDATE
... WHERE excluded.updated_at >= 现有 updated_at`，新者胜）：

| 方法 | 作用 |
| --- | --- |
| `upsert_city_evidences(city, rows)` | 写正文；`(city, evidence_key)` 冲突时按 `updated_at` 取新 |
| `get_city_evidence_rows(city)` | 读正文行（时间有效性由 city_cache 统一判断） |
| `upsert_city_cache_meta(city, *, social_queries, social_served_queries, updated_at)` | 写检索词计划与"真正搜过"的检索词 |
| `get_city_cache_meta(city)` | 读检索词 |
| `prune_city_cache(city, *, guide_before, poi_before)` | 按各自 TTL 阈值删 `city_evidences` / `city_poi_mentions` / `city_pois` 的超期行，返回删除行数 |

### 6.2 `app/city_cache.py`

```
CityCacheHit
  + evidences: list[Evidence]                 # 攻略正文
  + social_queries / social_served_queries    # 检索词
  payload(*, include_evidence_text=True)      # 公开接口传 False

read_candidates(city, *, store, now, allow_stale, evidence_limit=None)
  · 多读 city_evidences 与 city_cache_meta

  · evidence_limit 默认取 config.evidence_max(=40)，与实时抓取同口径

write_candidates(city, places, evidences, *, store, updated_at,
                 social_queries=None, social_served_queries=None)
  · 写 POI / 提及 / 正文 / 检索词
  · 末尾调 prune_city_cache()，阈值 = timestamp − 各自 TTL

_evidence_key(evidence)     → sha1(url + title)[:20]（无 URL 时退到 provider+source_type+标题+发布时间，再退到正文前缀）
_evidence_rows(...)         → 跳过"没正文、没提及、没菜品"的空壳

```

### 6.4 `app/workflow.py`（最关键的一处）

```python
STATUS_CACHED = "CACHED"   # 刻意不复用 Provider 词表里的 OK：
                           # 这条证据不是本次调用拿到的，写 OK 会让审计看起来像"这次真的打了 Provider"

def _materialize_city_evidence(store, run_id, bundle) -> list[dict]:
    """把城市知识库里的攻略正文过户成本次 run 的 sources + Evidence。"""

    # 只有 bundle.city_cache.source == "city_cache" 且有证据时才动作
    for index, evidence in enumerate(evidences, start=1):
        source_id = f"{run_id}-cache-{index:03d}"            # ← 必须重新分配
        store.save_source(run_id, {
            "source_id": source_id,
            "provider": evidence.provider,
            "source_type": evidence.source_type,
            "source_url": evidence.source_url,
            "query": {},                                     # 本次没发过查询，留空而不是编一个
            "fetched_at": evidence.fetched_at or cached_at,   # ← 保留原始抓取时间
            "status": STATUS_CACHED,
            "normalized": {"origin": "city_cache", "city_cache_updated_at": cached_at},
        })
        adopted.append(evidence.model_copy(update={"id": f"{source_id}-cached",
                                                  "source_id": source_id}))
    bundle.evidences = adopted                               # ← 就地替换，下游看到的是 run 级 id
    bundle.degradations.append("攻略正文复用城市知识库缓存（N 条，最早抓取于 …），本次未重新检索社媒；…")
```

调用点（**必须在跑图之前**，否则外键会挡住 evidence 插入）：

```python
adopted_calls: list[dict[str, Any]] = []
cached_evidence: list[dict[str, Any]] = []
if prefetch is not None:
    adopted_calls = _adopt_prefetch_sources(resolved_store, resolved_run_id, prefetch)
    cached_evidence = _materialize_city_evidence(resolved_store, resolved_run_id, prefetch)
...
state = {..., "adopted_calls": adopted_calls, "cached_evidence": cached_evidence, ...}
```

### 6.6 数据流对照

```
【改动前】会话 2（命中城市缓存）
  city_pois → places ✅
  city_poi_mentions → 只用来填 result_count
  正式 run → bundle.evidences 为空 → query_expansion(LLM) → 社媒检索 → 模型抽取地点
                                   ↑ 最贵的三段全部重付

【改动后】会话 2（命中城市缓存）
  city_pois          → places ✅（不查 search_poi）
  city_evidences     → bundle.evidences ✅ → node_search_social 直接返回（一个社媒 Provider 都不打）
                                          → _discovery_already_extracted 命中 → 地点抽取也不调模型
  city_cache_meta    → bundle.social_queries ✅（不调 query_expansion）
  跑图前             → _materialize_city_evidence 重建 run 级 sources/evidence（status=CACHED）
  交通 + 酒店        → 照旧实时查（不变，这是对的）
```

## 9. 谁把缓存填上：预热脚本

上面做完的是**读路径与写路径**，但"什么时候第一次有数据"仍然只能等第一个用户来踩：
他去成都的那次会话照样要把最贵的社媒检索 + 模型抽取全价付掉。**预热**就是把这段挪到离线。

`scripts/preheat_cities.py`：

```bash
python scripts/preheat_cities.py                    # 默认 20 个城市；只补空 / 过期的
python scripts/preheat_cities.py --cities 成都 重庆
python scripts/preheat_cities.py --retry-degraded   # 社媒恢复后，把无社媒证据的城市补回来
python scripts/preheat_cities.py --force            # 全部重跑
python scripts/preheat_cities.py --list             # 只看现状，不跑
```

默认清单 20 个城市（`scripts/preheat_cities.py::DEFAULT_CITIES`）：6 个热门（成都 / 重庆 / 西安 /
北京 / 上海 / 杭州）+ 14 个覆盖不同地域的（厦门 / 泉州 / 福州 / 黄山 / 合肥 / 钦州 / 桂林 /
长沙 / 武汉 / 青岛 / 洛阳 / 婺源 / 大理 / 三亚）—— 刻意混了中小城市，用来验证这条链路
不是只对一线城市有效。

它复用 `sessions.refresh_city_cache()`，所以**没有任何新的取数逻辑**：

- 构造的 intent 只有目的地、没有出发地和日期，`fetch_transport_candidates` /
  `fetch_hotel_candidates` 会自己跳过（`app/discovery.py:158`）—— 只跑「攻略 + 地点抽取」
  两条线，机酒价格与时刻表永远不进缓存（不变量 1 不受影响）；
- 写的还是那四张表，所以"预热出来的"和"用户自然形成的"是同一种数据，**读路径一行都不用改**；
- 脚本默认拒绝写本地 SQLite（除非 `--allow-sqlite`）：预热的意义就是写所有人共用的库。

**为什么不能在 Render 上跑**：线上是 512Mi 单实例，预热一跑就跟健康检查抢 CPU 与数据库
连接，会把正在服务的请求拖死（见 [09_部署说明.md](09_部署说明.md) §7 的 OOM 与探针超时实测）。
预热**只在本地 / CI 跑**，只要求写同一个库（Neon）。

### 9.1 一个必须盯住的降级：社媒不可用

`tikhub` 的免费额度很容易打完，顺序通常是先 HTTP 429 限流、再 `FREE_CREDIT_EXHAUSTED`
（余额归零，代码**拒绝继续调用**以免产生费用，见 `providers` 里的免费额度守则）。
无论哪种，社媒那条线都拿不到任何证据，只剩网页搜索，但流程仍然"成功"——
POI 有、正文有，**只是没有任何小红书 / 抖音证据**。这种结果会被后续会话当成
"攻略已就绪"吃满一个 TTL，而它其实是降级的。

所以 `refresh_city_cache()` 现在返回一份摘要（写入条数 + `social_evidences` + `notes`），
脚本据此把这类城市单独标成**降级**并逐条打印原因（连失败的检索词都列出来）。

**默认不重跑降级城市**：社媒不可用时重跑也是白跑，还会白烧网页搜索与高德 POI 的配额；
判断"什么时候值得重试"是人的判断，脚本不替用户猜。要补社媒得显式加
`--retry-degraded`（脚本在结束时会打印带这个开关的现成命令）。

判据 `sessions.is_social_evidence()` 与 `providers._evidences_from_social` 的写法对齐
（它固定写 `source_type="social"`），另容忍一次 provider 名。

### 9.2 2026-09-21 两次预热的实测结果

两批共 **20 座城市**全部落库（第一批 6 城 949s，第二批 14 城 2145s，每城约 2.2~2.8 分钟）：

| 批次 | 城市 |
| --- | --- |
| 一 | 成都 / 重庆 / 西安 / 北京 / 上海 / 杭州 |
| 二 | 厦门 / 泉州 / 福州 / 黄山 / 合肥 / 钦州 / 桂林 / 长沙 / 武汉 / 青岛 / 洛阳 / 婺源 / 大理 / 三亚 |

每座城市都拿到 **20 个高德核实过的 POI** + **6~22 篇网页正文** + **12~16 个检索词**；
中小城市与县域（钦州、婺源、黄山）与一线城市表现一致，没有出现落库为 0 的情况。

但 **20 座城市全部是降级结果**（`social_evidences = 0`）：

| 现象 | 证据 |
| --- | --- |
| 第一批：`tikhub/search_xiaohongshu` = `RATE_LIMIT`（HTTP 429） | `python scripts/provider_smoke.py --only tikhub` |
| 第二批：`FREE_CREDIT_EXHAUSTED`（`balance=0.0`，代码拒绝调用） | 同上 |
| `mediacrawler` 回退不可用（需要本地浏览器会话） | 状态 `UNAVAILABLE` |
| 落库证据全部来自网页 | `city_evidences` 里 `source_type='web' / provider='tavily'` |
| 脚本如实标出降级并列出来因 | `preheat_cities.py` 结束时打印"降级（N 座）"与失败的检索词 |

也就是说：**缓存是可用的**（POI 真实、网页正文真实、检索词能省掉 `query_expansion`），
但攻略的社媒那半缺失。这不是脚本的问题 —— 等 `tikhub` 恢复（充值或额度重置）后
用 `--retry-degraded` 重跑即可覆盖，**不需要清库**：

```bash
python scripts/preheat_cities.py --retry-degraded --cities 成都 重庆 西安 北京 上海 杭州 \
    厦门 泉州 福州 黄山 合肥 钦州 桂林 长沙 武汉 青岛 洛阳 婺源 大理 三亚
```

## 10. 一句话总结

**缓存的价值不在"存了多少张表"，而在"最贵的那一段有没有被省掉"。**
原来的城市知识库只省掉了高德 POI 检索，把最贵的社媒检索与模型抽取留在了每个会话里；
补齐攻略正文与检索词之后，第二个去同一座城市的会话才真正"零社媒、零抽取"，
而代价是三处必须同时做对：**正文要落库、要进 bundle、复用时必须重建 run 级 provenance**。
