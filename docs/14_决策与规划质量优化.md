## 1. 当前问题

目前 TravelPlan 的主要问题不是 12-step Workflow，而是**旅行决策过于依赖固定 Python 权重**。

例如现在类似：

```text
酒店分数
= 价格权重
+ 评分权重
+ 位置权重
+ 偏好权重

景点分数
= Trust
- Ad Risk
+ 用户偏好
+ 路线分
```

这种方式稳定，但容易得到「数学上合理、实际体验一般」的结果。

典型问题：

- 酒店便宜、评分高，但离美食和商圈很远
- 景点排名高，但一天来回跑
- 餐厅只是普通 POI，没有真正根据午餐/晚餐位置选择
- 不同用户最后使用的决策规则差别不大
- 用户明明说「主要想吃」，系统还是按照固定景点权重规划
- Python 在替用户决定「什么是好旅行」

---

## 2. 核心优化原则

新的职责划分：

```text
Provider
↓
提供真实数据

LLM
↓
理解用户真正喜欢什么
生成 Dynamic Preference Profile

Python
↓
根据动态偏好计算候选 / Top-K

LLM
↓
必要时从 Top-K 做软选择

Python
↓
只做最终真实性和可执行性检查

Final Plan
```

核心原则：

> Python 不负责定义「什么旅行最好」，Python 只负责保证旅行真实、合理、能执行。

---

## 3. Python 只保留真正的硬规则

这些继续由 Python 严格判断：

```text
地点必须真实存在
酒店必须真实存在
真实价格不能伪造
路线不能伪造
时间不能物理冲突
营业时间不能明显冲突
返程必须赶得上
REJECT 地点不能出现
MUST 地点不能无原因丢失
用户明确说「预算绝对不能超过」时不能超
```

其他全部改成**软决策**。

例如：

```text
住春熙路还是天府广场？
酒店贵 100 元但位置很好，值不值？
一天安排 2 个还是 4 个景点？
火锅是专门绕路去吃还是附近找一家？
评分 4.8 但偏远 vs 评分 4.6 但楼下就是商圈？
```

这些不应该再由固定 Python 权重直接决定。

## 4. Dynamic Preference Profile

用户输入或 Guided Mode 完成后，由 LLM 生成一份本次旅行专属的动态偏好。

例如用户说：

```text
去成都3天，主要想吃东西和逛街，
喜欢热闹，晚上想出去逛，
景点不用安排太多。
```

生成：

```json
{
  "travel_style": "food_commercial_centered",

  "hotel_area": {
    "food_density": 0.30,
    "commercial_area": 0.25,
    "nightlife": 0.18,
    "transit": 0.12,
    "poi_centrality": 0.08,
    "price": 0.05,
    "quietness": 0.02
  },

  "hotel": {
    "location": 0.30,
    "food_access": 0.25,
    "rating": 0.15,
    "transit": 0.15,
    "price": 0.10,
    "comfort": 0.05
  },

  "attraction": {
    "user_interest": 0.30,
    "route_fit": 0.30,
    "evidence": 0.15,
    "iconic": 0.10,
    "photo_value": 0.10,
    "popularity": 0.05
  },

  "food": {
    "local_recommendation": 0.25,
    "distance": 0.25,
    "specific_dishes": 0.15,
    "evidence": 0.15,
    "ad_risk": 0.10,
    "rating": 0.05,
    "price": 0.05
  },

  "pace": {
    "target_poi_per_day": 2,
    "prefer_free_time": true
  }
}
```

如果用户换成：

```text
带父母去成都，轻松一点，
不要走太多路，酒店安静一点。
```

Profile 自动变成：

```text
酒店：
交通便利 ↑
安静 ↑
距离景点近 ↑
夜生活 ↓

景点：
少走路 ↑
顺路 ↑
休息时间 ↑
景点数量 ↓

餐厅：
距离 ↑
排队时间 ↓
环境舒适 ↑
网红程度 ↓
```

这样才能真正做到：

> 不同用户 → 不同规划逻辑。

## 5. Guided Mode 增加住宿策略

> **实现状态**：Guided 里**已经有**"住宿策略"这一步，但选项名与本文不同——真实枚举是
> `selection.HOTEL_PRIORITIES = value / location / rating / comfort / transit / auto`
> （性价比优先 / 位置优先 / 评分优先 / 舒适优先 / 交通方便 / 帮我选）。
> 本文写的"商圈·美食优先 / 景点居中 / 安静舒适"**没有**成为按钮；"美食密度、商圈密度、
> 夜间便利"这类区域级判断由 LLM 画像在 `discovery.extract_hotel_areas()` 里承接，
> 不由这个按钮直接驱动。

增加：

```text
你更希望住在哪里？

○ 商圈 / 美食优先
○ 景点居中
○ 交通方便
○ 性价比
○ 安静舒适
○ 帮我选择
```

例如选择：

```text
商圈 / 美食优先
```

动态提高：

```text
攻略推荐住宿区域
美食密度
商圈密度
夜间便利
地铁便利
```

降低：

```text
绝对最低价格
离所有景点几何中心最近
```

## 6. 优化后的完整规划流程

### Step 1：确认用户意图

得到：

```text
出发地
目的地
日期
天数
人数
预算
交通偏好
住宿偏好
旅行兴趣
节奏
MUST / WANT / REJECT
```

Guided Mode 的结构化选择优先，不再让 LLM 重新猜。

### Step 2：生成动态偏好

LLM 根据用户信息生成：

```text
Dynamic Preference Profile
```

决定这次旅行：

```text
什么最重要
什么次要
什么基本不重要
```

### Step 3：查询大交通

查询：

```text
12306
途牛航班
```

确定：

```text
真正几点到目的地
真正几点离开
首日剩多少时间
最后一天剩多少时间
```

交通候选也使用动态偏好：

```text
有人价格优先
有人时间优先
有人不接受红眼
有人宁可贵一点也不浪费第一天
```

> **实现状态：未实现。** 交通排序走 `selection.transport_weights()`，权重来自
> `PlannerTuning` 与 `intent.transport_mode / transport_priority / transport_constraints`
> 这些**意图字段**；`PreferenceProfile` 里没有 transport 组，交通比选读不到画像。
> 也就是说"有人价格优先 / 有人时间优先 / 不接受红眼"目前由 Guided 的交通步骤表达，
> 不是由 LLM 画像推断的。

### Step 4：攻略研究

搜索：

```text
小红书
抖音
Web
```

重点搜索：

```text
当地必去
当地美食
避坑
推荐住宿区域
商圈
夜生活
用户兴趣相关内容
```

得到 Evidence。

## 7. 候选生成要拆成不同池

> **实现状态：三池，不是四池。** `discovery.POOL_KEYS = ("attraction", "food", "experience")`；
> "住宿区域"是**独立产物**（`discovery.extract_hotel_areas()`），不在这三个池里。

不要再把所有地点统一当成普通 POI。

应该形成：

```text

九眼桥

火锅
串串
川菜

体验：
喝茶
川剧
夜游锦江
掏耳
```

## 8. 高德负责真实性验证

高德不是负责决定「值得不值得去」。

高德负责：

```text
这个地方是否真实
在哪里
经纬度
类型
地址
营业时间
附近有什么
真实路线
```

攻略 Evidence 负责：

```text
大家是否真的推荐
具体推荐什么
是不是广告
是不是本地人常去
是否长期有人提
```

## 9. 先选择住宿区域

> **实现状态：已实现，但选区域用的是确定性动态权重，不是本文建议的 LLM Soft Ranking。**
> `discovery.extract_hotel_areas()` 按攻略证据与画像算出每个区域的 `fit_score`，直接取 Top-K
> （区域数上限写在 `discovery` 里的产品常量，不进 `config`）。

这是本次改造的重要变化。

不要直接从全部酒店中挑一家。

先判断：

```text
这次旅行最适合住哪个区域？
```

候选区域综合考虑：

```text
攻略推荐度
美食密度
商圈密度
夜间便利
地铁便利
到机场/车站便利
核心景点覆盖
用户偏好
```

例如：

```text
用户：
主要为了吃、逛街、晚上出去玩

结果：

春熙路
美食：高
商圈：高
夜生活：高
交通：高

天府广场
交通：高
景点中心性：高
美食：中

→ 春熙路更符合本次用户
```

这里可以使用：

```text
动态权重 Top-K
+
LLM Soft Ranking
```

而不是固定公式直接决定。

## 12. 景点按区域规划

> **实现状态：区域聚类已做，"每天几个点"仍由固定阈值决定。**
> `planner.cluster_places()` + `_area_name()` 已经按区域给每天成骨架；
> 每日点位容量取 `PlannerTuning.max_items_per_day`，**不是** `profile.pace.target_poi_per_day`
> ——后者目前只出现在进度文案里，全库没有消费点。

景点不要一个一个全局排名然后硬塞。

先做区域聚类：

```text
Day 1
武侯祠 / 锦里区域

Day 2
熊猫基地 + 春熙路区域

Day 3
宽窄巷子 / 人民公园区域
```

原则：

```text
每天主要玩一个区域
每天 2~4 个核心点
尽量少跨城
尽量不折返
留出吃饭和自由活动时间
```

具体数量根据 Dynamic Preference Profile 决定。

## 13. 美食单独规划

> **实现状态：与本节描述不同。** 现状是"从当天**已有候选**里拆出 food 类，按午餐/晚餐时间窗插入，
> 并优先取离当天景点近、有攻略支撑的"（`planner._insert_meals`）。**没有**"以当前位置为圆心重新向高德
> 检索附近真实餐厅"这一步；`profile.food` 的六个权重当前**没有任何消费点**（画像只驱动 hotel 与 attraction）。
> 本节描述的"当天位置 → 附近 1.5km → 重新找 8 家餐厅"仍是待做项。

美食不能继续和景点使用同一套 POI 排序。

正确逻辑：

```text
当天景点骨架
↓
现在12点，人在哪里？
↓
附近有哪些真实餐厅？
↓
哪些在攻略里反复推荐？
↓
哪些具体菜品值得吃？
↓
营业吗？
↓
需要绕路多少？
↓
选择午餐
```

晚餐同理。

例如：

```text
17:30 在春熙路
↓
附近 1.5km
↓
找到 8 家真实餐厅
↓
结合：
小红书 Evidence
具体菜品
Ad Risk
距离
营业时间
用户口味
↓
选择晚餐
```

而不是：

```text
成都评分最高餐厅
↓
不管距离直接塞进行程
```

## 14. 最后才查询真实 Route

等真正决定：

```text

景点
餐厅
```

以后再查：

```text
酒店 → 景点A
景点A → 午餐
午餐 → 景点B
景点B → 晚餐
晚餐 → 酒店
```

避免提前查询大量最终根本不会使用的路线。

## 16. Top-K + LLM Soft Ranking

Planner 可以先生成：

```text
Plan A：美食 / 商圈体验最好
Plan B：最顺路
Plan C：更轻松
```

它们都已经通过 Python 可行性校验。

然后 LLM 根据 Dynamic Preference Profile 选择：

```text
哪一个最符合这个用户？
```

LLM 不允许修改真实：

```text
价格
营业时间
路线
交通时间
POI
```

只负责软选择。

## 17. Jev 改成可选能力

> **实现状态：已实现，但降级链比本节多一个前提。** 真实顺序是
> `Jev → LLM Ranking → 动态权重 Top-1`，且**只有 Jev 真的被调用过（`attempted=True`）而失败时**
> 才会落到 LLM Ranking；若 Jev 未配置 / 未开启 / 熔断已开（`attempted=False`），
> 会**直接**走动态权重 Top-1，不再多付一次 LLM 调用（`app/decision/planner_decision.py:342-351`）。
> 另外硬约束可行的候选只剩一份时，`choose_plan` 直接返回该方案，连 Jev 都不问（`app/workflow.py:3282-3290`）。

Jev 不再是关键路径：

```text
Jev 可用
→ 可以参与 Top-K 判断

Jev 不可用
→ 普通 LLM Ranking

LLM Ranking 失败
→ Dynamic Weight Top-1
```

因此：

```text
Jev = Enhancement
不是 Dependency
```

## 最终目标

TravelPlan 不应该是：

```text
固定权重
+ POI 排名
+ 自动塞进行程
```

而应该变成：

```text
理解这个用户怎么玩
↓
动态改变本次旅行的决策标准
↓
基于真实数据生成候选
↓
像真人一样围绕住宿、区域、美食和景点做取舍
↓
Python 最后保证它真的能执行
```

核心原则：

> **LLM 决定「这个用户会喜欢什么」，Python 只负责「这个方案到底能不能真的走」。**
