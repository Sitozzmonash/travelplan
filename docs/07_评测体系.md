# 07 评测体系

一句话：用一批固定的、可复现的用例，把"这次改动让行程变好还是变坏"变成数字。

完整说明（case 格式、指标口径限制、如何加 case）在 [`benchmark/README.md`](../benchmark/README.md)，
本篇只讲清"体系长什么样、数字怎么读、跟 BadCase/Evolution 怎么接"。

## 1. 构成

```text
32 例确定性 Core Case（离线、可复现、不消耗第三方额度）
├─ basic                12  人工典型需求（国内城市，预算/人数/偏好各不相同）
├─ hard                  6  边界条件（当天往返、跨天卧铺、末日返程、无日期、无预算、只玩 1 天）
├─ badcase_regression    6  已确认的真实失败类别，一条一个
├─ provider_failure      4  受控注入（Provider 失败 / 返回空）
└─ jev_decision          4+1 关键软决策与 fallback（多出的一条覆盖"结构不合法"）

5 例 Live Smoke（联网，单独统计，不进确定性指标）
```

> 关于数量：任务要求的 4 个 Jev 决策用例之外，额外加了一条 `jev_plan_choice_fallback_on_invalid`
> （返回结构不合法 → 兜底 + 留 Bad Case），因为这是线上最容易被忽略、后果又最长的失败模式。
> 因此确定性用例是 33 而不是 32。

**Bad Case 一旦确认，就永久加入 `badcase_regression.jsonl`** —— 这是"不重复犯同一个错"的机制。

## 2. 指标（六维，全部由代码从既有事实算出）

| 维度 | 关心什么 | 代表指标 |
| --- | --- | --- |
| hard_constraints | 行程本身对不对 | `date_mismatch_rate`、`hard_time_conflict_rate`、`opening_hours_violation_rate`、`missing_*_disclosure_rate`、`budget_math_error_rate`、`hallucinated_price_rate`、`hallucinated_route_rate`、`missing_source_rate` |
| plan_quality | 行程好不好 | `category_diversity`、`backtracking_score`、`daily_load_balance`、`meal_time_quality`、`pace_match`、`preference_coverage`、`first_day_quality`、`last_day_quality`、`route_efficiency` |
| evidence | 推荐有没有依据 | `evidence_coverage`、`multi_source_ratio`、`poi_verified_ratio`、`unsupported_recommendation_rate` |
| provider | 数据源稳不稳 | `provider_success_rate`、`fallback_success_rate`、`timeout_rate` |
| performance | 代价多大 | `end_to_end_latency`、`llm_latency`、`jev_latency`、`provider_latency`、各类调用次数与 token |
| jev | 软决策值不值 | `jev_success_rate`、`jev_fallback_rate`、`jev_timeout_rate`、`jev_low_confidence_rate`、`jev_plan_accept_rate`、`jev_replan_rate`、`quality_delta_with_jev`、`latency_delta_with_jev` |

三条读法上的约定：

1. **`null` ≠ 0**。`null` 是"这次没有可测对象"，0 是"确实是零"。混起来 OFF/ON 对比会得出错误结论。
2. **软指标不能掩盖硬错误**。`quality_delta_with_jev` 用的质量代理只取
   `preference_coverage` 与 `pace_match` 的均值，硬约束类指标不参与平均 ——
   硬约束一旦变差就单独看。
3. **`hard_constraint_violation_rate` 的分母是"天数 + 5"**，只用于版本间比较，不是"违规概率"。

口径限制（不要误读）写在 `benchmark/README.md` 的"已知的指标口径限制"一节。

## 3. 基线（Jev OFF vs ON）

一份基线记：`benchmark_version / travelplan_commit / superharness_commit / model /
fixture_version / config 快照 / suites / case_count / passed / failed / metrics / generated_at`。

- **Baseline A = Jev OFF**：不注入替身，走真实的"未配置/关闭"分支，且**不跑** `jev_decision`
  套件、**跳过**标了 `requires_jev: true` 的用例（前提不成立，跑出来全是假 fail）。
- **Baseline B = Jev ON**：注入脚本化假 Jev，走完整的三处软决策。

两份基线必须**成对更新**（同一个 commit、同一个 fixture 版本）；只更新一边，
`baseline_compare` 就是在拿两个不同的世界做对比。改 `FIXTURE_VERSION` 后必须两份都重跑。

生成与查看：

```bash
python -m benchmark.runner --jev off     # 更新 baselines/jev_off.json
python -m benchmark.runner --jev on      # 更新 baselines/jev_on.json（并算出 baseline_compare）
```

管理端 `/admin/benchmark` 会展示六个维度、逐 case 结果（按套件分组）、以及 Jev OFF vs ON 的对照。

## 4. 与 BadCase / Evolution 的关系

```text
Run → 规则检测 → Bad Case(pending)
                     │
                     ├─► 人工确认后：把触发场景写进 badcase_regression.jsonl（永久回归）
                     │
                     └─► Evolution：聚类 → 候选改动 → 调 benchmark.runner.make_measure()
                                    在同一批用例上跑「改动前 vs 改动后」→ ACCEPT / REJECT
```

`make_measure(store, suites=("hard","basic"))` 返回一个 `measure(overrides) -> 指标`，
在**临时库**里跑，不污染生产库。判定规则见 [08_进化机制.md](08_进化机制.md)。

## 5. 什么时候必须跑

| 改动 | 必须跑 |
| --- | --- |
| `app/planner.py`（打分/排程/预算/可行性） | `python -m benchmark.runner --jev on`，并与 baseline 对比 |
| `app/prompts.py` | 至少跑 `--suite basic --limit 4`（模型侧变化无法单测） |
| `app/providers.py` / 能力插件 | `--suite provider_failure` |
| Jev 相关（`app/decision/`、`JEV_*` 配置） | 两份基线都要重跑（OFF 与 ON） |
| 只改文档/前端 | 不需要，但 `pytest` 与前端 typecheck/lint/build 仍要过 |

## 6. Benchmark 与 Guided Journey 的关系

**Benchmark v0.1 的结构没有变**（`benchmark/cases` 五个确定性套件 + live_smoke、六维指标、
OFF/ON 基线、判卷器都照旧）。引导式旅程刻意**不改变确定性评测的口径** —— 把"六步向导好不好用"混进
核心 Planner 总分，只会让"这次改动让行程变好还是变坏"这个数字变得不可解释。

引导式旅程的验证独立成两套**离线**单测/接口测试：

| 文件 | 条数 | 守什么 |
| --- | --- | --- |
| `tests/test_guided_journey.py` | 18 | REJECT 硬排除 / MUST·WANT 加分 / `resolve_pace` 确定性 / `discovery.prefetch` 与 `PrefetchBundle` 类型化往返 / Session create-patch-start 幂等 / 取消后 start=409 / `intent_from_basic` 不调模型 |
| `tests/test_admin_observability.py` | 15 | Admin Planning Session 列表·筛选·详情信封·Session→Run 关联 / Provider Health 聚合·无历史=UNKNOWN·失败与 fallback 统计·脱敏·鉴权 |

它们与 Benchmark 共用 `tests/fakes.py` 的离线假件（`FakeHub` / `FakeLLM` / `FakeJev`），
所以"单测通过、评测失败"不会变成无法归因的分歧。

跑法：`python -m pytest -q`（全量离线）。**改 `benchmark/cases` 或 `FIXTURE_VERSION` 时，两份基线都要重跑**；
只改引导式代码不要求重跑基线，但 pytest 必须全绿。

## 7. 已知未覆盖的部分（诚实说明）

- **没有 LLM Judge**。v0.1 只判"客观事实对不对"（日期、披露、来源、Bad Case 是否留下）。
  "这份行程好不好玩"用可复现的软指标近似，不做主观打分。
- `poi_verified_ratio` 用的是"行程项是否带 source 引用"这个代理，不是真的查高德校验标记。
- Live Smoke 只有 5 条，且只验证"链路能通"，不参与指标。
- Benchmark 跑的是注入假件的离线世界；它能证明"逻辑没退化"，不能替代真实 Provider 抽检
  （真实链路的抽检见 `scripts/provider_smoke.py` 与 `--live`）。
