# 03 项目流程图

一句话：用纯文字图说明一次规划从头到尾经过哪些环节、每个环节谁负责、失败了怎么办。

## 1. 总览

```text
用户请求（自然语言）
   │
   ▼
[1] Workflow（app/workflow.py：固定 12 步，Python 决定"做什么"）
   │
   ├──► Provider / Tool / MCP（app/providers.py + super_harness）
   │        真实价格 / 车次 / 航班 / 酒店 / 门票 / 路线 / 攻略
   │        每个 Provider 都有主备：12306 主、途牛备；TikHub 主、MediaCrawler 备
   │        失败 → 记 status + 降级说明，继续（绝不编数据）
   │
   ├──► Python 硬规则（app/planner.py：无网络、无随机、可脱网单测）
   │        去重 / Trust / Ad Risk / 候选打分 / 地理聚类 / 排程 / 预算 / 时间与营业时间约束
   │
   ├──► Planner Top-K（app/planner.py:build_plan_variants）
   │        Python 排出若干份**同样满足硬约束**的候选行程（只改区域先后策略）
   │
   ├──► Jev 关键软决策（app/decision/planner_decision.py，最多 3 次调用）
   │        A 方案选择：多份候选里挑整体更好的
   │        B 关键 Trade-off：当前方案 vs 其它候选，或 REPLAN
   │        C 质量门：KEEP / REPLAN（附 pace / preference / diversity / confidence 软分）
   │        超时 / 429 / 401 / 结构不合法 / 低置信度 → 记 Trace + fallback + 确定性继续
   │
   ├──► Python 硬约束复核（app/planner.py:hard_constraint_violations）
   │        Jev 选中的方案必须再过一次；不通过 → 退回默认方案并记 jev_wrong_choice
   │
   ▼
Final Plan（plan.json / plan.md）
   │
   ├──► Trace（trace_spans 表 + outputs/<run_id>/trace.jsonl）
   │        workflow / llm / jev / provider / tool / mcp / planner / budget / feasibility / critic / store
   │
   ├──► Bad Case（app/badcase.py，规则检测，不调模型）
   │        落 badcases 表 + badcases.json，计数进 run_metrics.badcase_count
   │
   ├──► Benchmark（benchmark/runner.py，离线可复现）
   │        32 例确定性 + 5 例 Live Smoke；Jev OFF / ON 两份基线
   │
   └──► Evolution（app/evolution.py）
            待分析 Bad Case → 聚类 → 候选改动 → 用 Benchmark 对比 → Experience
            （不自动改代码、不自动上线）

最终呈现：用户端（frontend/app/**）/ 管理后台（frontend/app/admin/**）
```

## 2. 12 步时序（每步：做什么 → 输入 → 输出 → 失败怎么降级）

```text
① parse_intent
   做什么：把自然语言变成 TripIntent（出发地/目的地/天数/日期/人数/预算/偏好）
   输入  ：原始 query
   输出  ：intent（落 trip_requests 表）
   降级  ：模型不可用 → 规则解析（_rule_based_intent）。连目的地都没有 → 直接结束并要求澄清（唯一分支）

② search_intercity_transport
   做什么：查去程/回程的大交通（火车主源 12306，机票/备选途牛）
   输入  ：origin / destination / 日期
   输出  ：transport_plan（selected + alternatives + 选择理由）
   降级  ：12306 失败 → 途牛；都失败 → 如实告知"没选到"，并在可行性阶段报"缺少交通披露"

③ search_hotels
   做什么：查住宿候选并按价格/评分/位置打分
   输出  ：hotel_plan
   降级  ：途牛返回空 → 报"缺少住宿披露"，预算里住宿记 0 并说明

④ search_social_guides
   做什么：搜小红书/抖音/网页攻略（TikHub 免费额度优先，MediaCrawler 兜底）
   输出  ：evidences（落 evidence 表，每条都带 provider / url / 抓取时间）
   降级  ：全部失败 → 后续地点只能靠高德 POI，Trust 的"多来源"分项会偏低

⑤ extract_and_normalize_places
   做什么：从攻略文本抽地名 → 与高德 POI 归一化/去重合并
   输出  ：places（落 places 表）
   降级  ：模型抽取失败 → 只用攻略自带地名与关键词候选

⑥ verify_poi_and_routes
   做什么：逐个点查高德 POI 详情（营业时间/地址）与点对点路线
   输出  ：amap_verified、routes、amap_status
   降级  ：高德失败 → 路线走"具名常量粗估"并标 verified=False，Critic 下调置信度

⑦ score_candidates
   做什么：算 Trust（六分项）与 Ad Risk（六分项）、综合候选分、查门票真实价
   输出  ：trust_scores / ad_risks / candidate_scores / ticket_prices + 每个点的 KEEP/REJECT 决策
   降级  ：门票查不到 → 该项不计入预算（不猜价格）

⑧ build_initial_plan   ← Top-K + Jev 方案选择在这里
   做什么：多套区域排序策略各排一版 → Jev 选整体更好的 → Python 硬约束复核
   输出  ：days、plan_candidates、plan_choice、quality
   降级  ：只有一份候选 → 不问 Jev（省一次调用）；Jev 失败/选错 → 用默认方案并记 fallback

⑨ check_budget
   做什么：真实花费与估算花费严格分开，对照用户预算
   输出  ：budget（含 breakdown 与省钱建议）
   降级  ：无预算 → status=unknown，只报预计总花费

⑩ check_feasibility
   做什么：时间冲突向后平移；返程赶不上则截断；营业时间排不下则**移除该点**
   输出  ：revised days + warnings（含 original → revised）
   降级  ：无法解决的冲突如实记为 error（会被 Critic 拒绝并进 Bad Case）

⑪ critic_and_revise   ← Jev Trade-off 与质量门在这里
   做什么：规则 Critic + 模型 Critic；然后 Jev 做取舍与 KEEP/REPLAN；REPLAN 则换候选并重跑可行性
   输出  ：critic、decisions、tradeoff、gate、必要时换掉 days
   降级  ：模型 Critic 失败 → 只有规则 Critic，并记降级说明

⑫ finalize
   做什么：按最终行程重算预算 → 模型成文（失败则纯代码成文）→ 落库 → 写六件产物
   输出  ：plan、plan_md、audit、badcases、outputs
   降级  ：成文失败 → plan.md 全部由代码生成（数字不经模型改写）
```

## 3. 谁负责什么（一条不能越界的线）

```text
硬事实 / 硬约束            → Python（app/planner.py）
真实价格/车次/路线/营业信息 → Provider / Tool / MCP（app/providers.py + super_harness）
关键模糊软决策             → Jev（app/decision/）
复杂生成与解释             → LLM（app/llm.py + app/prompts.py）
```

推论（也是评审时要问的问题）：

- 行程里的每一个数字都必须能指回一次 Provider 调用或一次代码计算，否则就是编造；
- 模型只在 5 处被调用（意图解析、检索词扩写、地点抽取、Critic、成文），
  它写的散文不能改结构化明细里的数字；
- Jev 的结论在落地前必须过 Python 的硬约束复核。

## 4. 状态机

```text
Run:  RUNNING ──► SUCCESS
              ├─► DEGRADED   （产出了行程，但有降级项）
              ├─► FAILED
              └─► CANCELLED

Span: WAITING → RUNNING → SUCCESS / WARNING / FAILED
```

`RUNNING → SUCCESS/DEGRADED/FAILED/CANCELLED` 是前端展示与轮询的唯一契约；
`runs.status` 保留小写旧值只为兼容历史接口，管理端一律读 `run_progress.status`。
