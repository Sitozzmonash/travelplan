# 03 项目流程图

一句话：用纯文字图说明"引导式准备（Guided Pre-Planning）"与"正式规划（Final Planning Workflow）"两段各自经过哪些环节、谁负责、失败了怎么办。

两者是**同一套引擎的两段**：Pre-Planning 只产出"可选候选"与"用户偏好"，正式 Workflow 才是原样保留的固定 12 步。

## 2. Session 状态机与事件时间线

Session 状态与 Run 状态**刻意分开命名**（`app/sessions.py`），不要混：

```text
COLLECTING ──► DISCOVERING ──► READY ──► STARTING ──►（正式 run）
     │              │            │
     └──────────────┴────────────┴──► CANCELLED / EXPIRED
```

```text
Run  （run_progress.status）：RUNNING → SUCCESS / DEGRADED / FAILED / CANCELLED
Stage（run_stages.status）  ：WAITING → RUNNING → SUCCESS / WARNING / FAILED
Span （trace_spans.status） ：RUNNING → SUCCESS / WARNING / FAILED
                              另有 SKIPPED —— "这一步本来就不该做"（route_skipped / poi_skipped，
                              component=planner，app/workflow.py:421-442 的 _skip_span）
                              与 REUSED —— 复用 Discovery 的结果（app/workflow.py:4910）
```

TTL 默认 45 分钟（`PLANNING_SESSION_TTL_MINUTES`）；过期判定在**每次读会话时**顺手做
（`store.expire_planning_sessions`），不依赖后台定时任务。过期会话标 `EXPIRED` 不删除。

事件时间线（存在 `planning_sessions.events_json`，管理端默认折叠）：

```text
session_created
discovery_queued
transport_prefetch_started / hotel_prefetch_started / social_discovery_started /
place_extraction_started
transport_prefetch_finished / hotel_prefetch_finished /
social_discovery_finished / place_extraction_finished
discovery_finished
discovery_failed
user_preferences_updated
session_confirmed / run_started
session_cancelled
```

> 四条线**都**写 `*_started`（transport / hotels / social / places，
> `app/sessions.py:304-311`）；过期也不只改状态 —— 读会话时会补写一条 `session_expired`，
> 让运维从时间线上就能看出原因（`app/sessions.py:167-173`）。
> 详见 [11_用户旅程与PlanningSession.md](11_用户旅程与PlanningSession.md) 第 9 节。

## 3. Guided Pre-Planning 细节：Prefetch 与逐阶段状态

```text
POST /api/v1/planning-sessions
  → sessions.create_session()：建会话（status=COLLECTING, discovery_status=PENDING）
  → 仅当 discovery_enabled 且 basic.destination 非空时，才切
    status=DISCOVERING / discovery_status=RUNNING 并提交后台 run_discovery()
    （app/sessions.py:152-157）；否则停在 COLLECTING、discovery_status=PENDING，
    等用户补全目的地

run_discovery()（app/sessions.py）
  → 先查城市知识库：city_cache.read_candidates(destination, store=store, allow_stale=True)
        （app/sessions.py:317）
        命中 / 过期 → _prefetch_with_city_cache()（app/sessions.py:434-480）：
             只实时查 transport + hotels；social / places 直接用 city_pois / city_poi_mentions
             （app/store.py:384-404），两阶段标 CACHE / STALE_CACHE；过期时后台再刷一次城市知识
        未命中 → discovery.prefetch(hub, llm, intent, hotel_pages=DISCOVERY_HOTEL_PAGES,
                 workers=DISCOVERY_WORKERS)
             （app/discovery.py:1079-1083 只把 transport / hotels / social 提交线程池 → 三线并行；
               :1099-1110 之后才**串行**跑 places，地点抽取依赖攻略结果）
        两条路每线都返回 {status, started_at, finished_at, duration_ms, result_count, degraded, error}
  → 还原成 PrefetchBundle，写回 session（transport/hotel/place 候选 + evidence_summary + stages）
  → 记录 provider_calls（source_type=discovery，无 run 外键）
  → discovery_status ∈ {PENDING, RUNNING, READY, PARTIAL, FAILED}：READY / PARTIAL 表示
    有可用候选；单线崩溃只记该线 FAILED + error，整轮跑不出来才置 FAILED
    （app/sessions.py:421），都不卡住用户
```

Discovery 只做到"给用户可选项"：POI 只核实存在性/类别/区域/证据条数（最多
`DISCOVERY_POI_VERIFY_LIMIT` 个查详情），**不两两算路线、不逐个查门票、不做完整 Feasibility/预算** —— 这些留给正式 Workflow。

## 4. 12 步时序（每步：做什么 → 输入 → 输出 → 失败怎么降级）

```text
① parse_intent
   做什么：把自然语言变成 TripIntent（出发地/目的地/天数/日期/人数/预算/偏好）
   输入  ：原始 query；Guided 下是用户确认过的结构化意图（state["intent_override"]）
   输出  ：intent（落 trip_requests 表）
   Guided 分支：直接采用结构化意图（不再让模型猜一遍），并按 resolve_pace_with_reason 推导节奏
   降级  ：模型不可用 → 规则解析（_rule_based_intent）。连目的地都没有 → 直接结束并要求澄清（唯一分支）

② search_intercity_transport
   做什么：查去程/回程的大交通（火车主源 12306，机票/备选途牛）
   输入  ：origin / destination / 日期；Guided 下优先复用 state["prefetch"]
   输出  ：transport_plan（selected + alternatives + 选择理由）
   复用  ：prefetch 有候选 → _reuse_result() 包成与 ProviderResult 同形（status/items/provider），
           不重复打 Provider，但仍按用户最终策略重新比选
   降级  ：12306 失败 → 途牛；都失败 → 如实告知"没选到"，可行性阶段报"缺少交通披露"

③ search_hotels
   做什么：查住宿候选并按价格/评分/位置打分
   复用  ：prefetch 有酒店候选 → 直接用（候选池比单页更宽）
   输出  ：hotel_plan
   降级  ：途牛返回空 → 报"缺少住宿披露"，预算里住宿记 0 并说明

④ search_social_guides
   做什么：搜小红书/抖音/网页攻略（TikHub 免费额度优先，MediaCrawler 兜底）
   复用  ：prefetch 有证据 → 直接返回 Discovery 证据（偏好变化只影响排序）
   输出  ：evidences（落 evidence 表，每条都带 provider / url / 抓取时间）
   降级  ：全部失败 → 后续地点只能靠高德 POI，Trust 的"多来源"分项会偏低

⑤ extract_and_normalize_places
   做什么：从攻略文本抽地名 → 与高德 POI 归一化/去重合并
   复用  ：Guided 下复用 Discovery places，并在此应用 MUST/WANT/REJECT（REJECT 硬排除）
   输出  ：places（落 places 表）
   降级  ：模型抽取失败 → 只用攻略自带地名与关键词候选

⑥ verify_poi_and_routes
   做什么：逐个点查高德 POI 详情（营业时间/地址）与点对点路线
   范围  ：只对会进入候选池的点做（REJECT 的点在 ⑤ 已被移出）
   输出  ：amap_verified、routes、amap_status
   降级  ：高德失败 → 路线走"具名常量粗估"并标 verified=False，Critic 下调置信度

⑦ score_candidates
   做什么：算 Trust（六分项）与 Ad Risk（六分项）、综合候选分、查门票真实价
   用户选择：对所有入口生效 —— REJECT 排除、MUST/WANT 加分（selection.preference_bonus）
   输出  ：trust_scores / ad_risks / candidate_scores / ticket_prices + 每个点的 KEEP/REJECT 决策
   降级  ：门票查不到 → 该项不计入预算（不猜价格）

⑧ build_initial_plan   ← Top-K + Jev 方案选择在这里
   做什么：多套区域排序策略各排一版 → Jev 选整体更好的 → Python 硬约束复核
   输出  ：days、plan_candidates、plan_choice、quality
   降级  ：只有一份候选 → 不问 Jev（省一次调用）；Jev 失败/选错 → 用默认方案并记 fallback

⑨ check_budget
   做什么：真实花费与估算花费严格分开，对照用户预算
   输出  ：budget（含 breakdown 与省钱建议）
   降级  ：无预算 → status=unknown，只报预计总花费

⑩ check_feasibility
   做什么：时间冲突向后平移；返程赶不上则截断；营业时间排不下则**移除该点**
   输出  ：revised days + warnings（含 original → revised）
   降级  ：无法解决的冲突如实记为 error（会被 Critic 拒绝并进 Bad Case）

⑪ critic_and_revise   ← Jev Trade-off 与质量门在这里
   做什么：规则 Critic + 模型 Critic；然后 Jev 做取舍与 KEEP/REPLAN；REPLAN 则换候选并重跑可行性
   输出  ：critic、decisions、tradeoff、gate、必要时换掉 days
   降级  ：模型 Critic 失败 → 只有规则 Critic，并记降级说明

⑫ finalize
   做什么：按最终行程重算预算 → 模型成文（失败则纯代码成文）→ 落库 → 写六件产物
   输出  ：plan、plan_md、audit、badcases、outputs；并写 user_journey 审计
   降级  ：成文失败 → plan.md 全部由代码生成（数字不经模型改写）
```

## 5. 谁负责什么（一条不能越界的线）

```text
硬事实 / 硬约束            → Python（app/planner.py）
用户点选如何影响结果        → Python（app/selection.py）
真实价格/车次/路线/营业信息 → Provider / Tool / MCP（app/providers.py + super_harness）
关键模糊软决策             → Jev（app/decision/）
复杂生成与解释             → LLM（app/llm.py + app/prompts.py）
```

推论（也是评审时要问的问题）：

- 行程里的每一个数字都必须能指回一次 Provider 调用或一次代码计算，否则就是编造；
- 模型在 **7 类**调用点被使用：意图解析、检索词扩写、地点抽取、Critic、成文，
  外加**动态偏好画像**（`app/decision/profile.py:78-79` 的 `PREFERENCE_PROFILE_PROMPT`）
  与**候选方案软排序**（`app/decision/planner_decision.py:201-202` 的 `PLAN_RANKING_PROMPT`
  / `llm_ranking`）；它写的散文不能改结构化明细里的数字；
- Jev 的结论在落地前必须过 Python 的硬约束复核；
- 用户明确点的 REJECT 在候选打分前就被硬排除，Jev 无法把它带回来。
