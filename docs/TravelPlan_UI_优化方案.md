## 1. 当前 UI 的核心问题

现在的 TravelPlan UI 最大问题不是单纯“丑”，而是整体更像一个 **AI Demo / 表单工具**，还不像成熟的旅行产品。

当前首页核心结构基本是：

```text
一句话输入
+ 高级条件
+ 开始规划
+ 几个说明卡片
```

主要问题：

- 缺少旅行感：没有目的地视觉、地图、住宿区域、美食、景点等旅行元素
- 默认入口还是“一句话直接规划”，真正重要的 Guided Mode 被放成次要入口
- 用户看不到系统在研究什么、为什么这么选
- 住宿、景点、美食的选择过程不够产品化
- 最终结果更像“AI 报告”，而不是能直接拿着走的旅行计划
- Trace / Trust / Evidence 等工程信息不应该成为用户主要视觉内容

---

## 2. UI 优化目标

目标不是继续做“一个更漂亮的 AI 输入框”，而是让产品更像：

```text
旅行发现
+
偏好选择
+
AI 研究
+
用户确认
+
智能规划
+
地图行程
```

体验上希望接近：

> Airbnb / Trip.com 的信息质感  
> + 小红书的旅行发现感  
> + AI Agent 的动态规划能力

---

## 3. 默认入口调整

当前：

```text
首页
→ 一句话输入
→ 直接开始规划

Guided Mode
→ 次要入口
```

建议改成：

```text
首页
→ Guided Mode（默认）

Quick Mode
→ “我已经想好了，直接一句话规划”
```

因为新的 TravelPlan 本身就依赖：

- 交通偏好
- 住宿策略
- 美食偏好
- 景点兴趣
- 节奏
- MUST / WANT / REJECT

这些信息应该成为正常规划流程的一部分。

---

## 4. 推荐的整体用户流程

```text
首页
↓
偏好向导
↓
Discovery / AI 研究
↓
探索确认页
↓
开始正式规划
↓
规划进度页
↓
最终行程
```

重点增加一个现在非常缺失的页面：

# 「探索确认页」

它是 Discovery 和正式 Run 之间的桥梁。

---

## 5. 首页

首页不要一上来就是一个大文本框。

建议核心内容：

```text
你想去哪里？

出发地：北京
目的地：成都
日期：10月1日
天数：3天

[开始规划]
```

下面保留：

```text
“已经想好了？用一句话快速规划”
```

作为 Quick Mode。

首页视觉可以增加：

- 热门目的地图片
- 最近规划
- 成都 / 重庆 / 杭州等目的地卡片
- “美食旅行 / 亲子 / 拍照 / 轻松度假”等旅行方式

让用户进入页面就有旅行感。

---

## 6. Guided Mode

Guided Mode 不应该只是普通表单。

建议拆成：

```text
Step 1 基础信息
Step 2 大交通偏好
Step 3 住宿策略
Step 4 旅行兴趣
Step 5 节奏
Step 6 确认
```

### 6.1 住宿偏好重点改造

不要只做普通 Radio：

```text
○ 商圈美食
○ 景点居中
○ 交通方便
```

建议做成卡片：

```text
┌──────────────────┐
│ 🍜 商圈 / 美食优先 │
│ 楼下就能吃，晚上方便逛 │
│ 适合：美食、夜生活      │
└──────────────────┘

┌──────────────────┐
│ 🏛 景点居中          │
│ 去主要景点距离比较均衡 │
│ 适合：第一次来        │
└──────────────────┘

┌──────────────────┐
│ 🚇 交通方便          │
│ 靠近地铁、火车站或机场 │
│ 适合：短途旅行        │
└──────────────────┘
```

选项：

- 商圈 / 美食优先
- 景点居中
- 交通方便
- 性价比
- 安静舒适
- 帮我选择

## 7. Discovery 期间不要让用户干等

用户填写基础信息后，后台可以开始：

```text
查交通
查酒店
搜小红书 / 抖音 / Web
提取 POI
发现住宿区域
```

前端逐步显示：

```text
✓ 找到 18 个航班 / 高铁候选
✓ 找到 42 家酒店
✓ 阅读 26 篇旅行攻略
✓ 发现 34 个景点和体验
✓ 发现 48 个美食候选
✓ 找到 4 个常被推荐的住宿区域
```

让用户感受到系统是在“研究旅行”，不是在等一个 LLM 回答。

---

## 8. 探索确认页

这是下一版最值得增加的页面。

### 8.1 推荐住宿区域

例如：

```text
我们找到 3 个比较适合你的住宿区域：

★ 春熙路 / 太古里
美食很多 · 商圈 · 夜生活 · 地铁方便
攻略推荐度：高
适合你：★★★★★

天府广场
位置居中 · 去主要景点方便
适合你：★★★★☆

宽窄巷子
旅游氛围强 · 景点近
适合你：★★★☆☆
```

用户可以：

```text
[选择春熙路]
[让我决定]
```

### 8.2 景点选择

```text
✓ 熊猫基地      必去
✓ 武侯祠        想去
○ 杜甫草堂      未选择
× 欢乐谷        不感兴趣
```

操作：

```text
MUST
WANT
REJECT
```

不要让用户自己输入 POI 名字，系统负责发现，用户负责简单选择。

### 8.3 美食偏好

不要直接让用户选几十家餐厅。

先让用户选：

```text
✓ 火锅
✓ 串串
✓ 川菜
○ 小吃
○ 甜水面
× 网红甜品
```

具体餐厅后面根据：

```text
当天位置
+ 距离
+ 攻略推荐
+ 营业时间
```

动态决定。

## 9. 正式规划中的 UI

不要只显示：

```text
正在规划...
```

应该展示真实阶段：

```text
✓ 已确定住宿区域：春熙路

✓ 正在比较附近酒店
  24 家 → 6 家候选 → 3 家最匹配

✓ 正在安排每天区域
  Day 1 武侯区
  Day 2 熊猫基地 + 春熙路
  Day 3 宽窄巷子

✓ 正在匹配午餐和晚餐
✓ 正在用高德检查路线
✓ 正在检查预算和返程时间
```

这样 AI 的价值是可见的。

```text

+

+

+

+

```

例如：

```text

¥420 / 晚

        建议游玩 2h
```

## 11. 地图应该成为核心 UI

最终行程至少需要：

```text
酒店
景点
餐厅
路线
```

全部能在地图看到。

每天切换：

```text
Day 1
Day 2
Day 3
```

地图同步切换路线。

用户应该能一眼看出：

> 今天是不是顺路。

---

## 12. 地点卡片展示内容

景点 / 餐厅卡片不要展示一堆工程字段。

主要展示：

```text
图片
名称
推荐原因
距离
预计停留时间
营业时间
价格
具体推荐内容
```

例如餐厅：

```text
XX火锅

距离当前景点 850m
18:00 营业
人均约 ¥90

为什么推荐：
- 多篇攻略重复出现
- 推荐菜：毛肚 / 黄喉
- 距离今晚住宿区域近
```

---

## 13. Evidence / Trust / Trace 怎么展示

这些能力重要，但不应该成为普通用户的主要页面。

普通用户看到：

```text
为什么推荐？
```

点击展开：

```text
小红书 4 条
Web 2 条
高德已验证
广告风险：低
```

完整的：

```text
Trust Score
Ad Risk
Provider Call
Trace
Source
Decision
```

放到“查看依据”或后台管理端。

## 16. 核心目标

当前产品更像：

```text
AI 输入框
→ 等
→ 给一份旅行报告
```

下一版应该变成：

```text
旅行发现
↓
表达偏好
↓
系统研究真实攻略和数据
↓
用户简单确认
↓
AI 智能规划
↓
地图 + 时间线形式的真实旅行计划
```

核心原则：

> **不要让用户感觉自己在“使用一个 Agent”，而应该让用户感觉自己正在“规划一次旅行”。**
